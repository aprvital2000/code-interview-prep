02 Kafka & Event-Driven Systems Deep Tech
A Kafka consumer group is falling behind at peak load — lag is growing and you have an SLA breach in 15 minutes. Walk me through your real-time triage process. Hints
Key angles to hit
They want to see production muscle memory. Cover: check consumer group lag (Kafka consumer group describe / Burrow / Datadog), isolate whether it's producer throughput spike or consumer slowdown (CPU, GC pauses, downstream DB locks). Short-term: scale consumer instances, check partition count (can't exceed partition count with more consumers), possibly temporarily disable non-critical downstream processing. Long-term: partition strategy review, consumer threading model, parallel processing within partition using virtual threads (Project Loom / Kotlin coroutines). Mention idempotent consumers so scaling doesn't cause duplicates.
KafkaIncident ResponseConsumer Lag
How do you implement exactly-once semantics across a Kafka-to-Postgres pipeline without destroying throughput? Hints
Key angles to hit
Cover Kafka's idempotent producers (enable.idempotence=true) and transactional API for exactly-once within Kafka. For the Kafka→Postgres boundary: outbox pattern (write event to DB in same transaction as state change, Debezium CDC to publish), or idempotency keys in the consumer (dedupe table with event_id, upsert pattern). Discuss the throughput cost: transactional Kafka adds ~20% overhead, and when that's acceptable vs. when at-least-once + idempotent consumers is the better trade-off for a prediction market.
KafkaPostgresExactly-OnceOutbox Pattern
How would you structure Kafka topics for a prediction market where you need per-market ordering, global audit log, and the ability to replay events for new services? Hints
Key angles to hit
Discuss event sourcing as the foundation: topic-per-aggregate vs. single compacted topic with event type headers. Partition key by market_id for ordering guarantees within a market. Retention: infinite retention (log compaction + time-based) for event sourcing replay capability. Separate audit topic with short-lived consumer that fans out to an append-only store (Postgres, Iceberg). Address schema registry versioning (backward/forward compat) so replaying old events into new consumers works. Mention Kafka Streams or Flink for stateful aggregations (live odds calculation).

03 Redis & Sub-Millisecond Latency Deep Tech
How would you use Redis to serve real-time market odds to thousands of concurrent users while keeping latency under 1ms p99? Hints
Key angles to hit
Cover Redis Cluster sharding by market ID, Pub/Sub or Redis Streams to push odds updates to subscribers rather than polling. Discuss connection pooling (Lettuce async), pipelining for batched reads, and avoiding hot keys by pre-aggregating odds into a single hash per market (HGETALL market:{id} vs. multiple GETs). For extreme latency: mention client-side caching (Redis 6 RESP3 tracking), and when Redis Cluster's cross-slot limitations matter. Mention monitoring: latency history, slowlog, and memory fragmentation as p99 killers.
RedisLatencyPub/Sub
Describe how you'd implement a distributed rate limiter in Redis for trade submission — one that's fair, fast, and survives a Redis node failure. Hints
Key angles to hit
Cover sliding window with Lua scripts (atomic ZADD + ZRANGEBYSCORE) for exactness vs. token bucket / fixed window for performance. Discuss Redlock algorithm and its controversies (Martin Kleppmann's critique) — and when a single-instance lock is actually safer. For failure: circuit breaker that falls back to local in-memory rate limiting with degraded (more permissive) limits. Mention Redis Cluster's issue with Lua scripts across slots and how to design keys to stay in the same slot ({user_id}.rate).

04 Kubernetes & AWS Platform
How do you design a Kubernetes platform that can handle 10x traffic spikes during a major sporting event with zero downtime? Hints
Key angles to hit
Cover HPA + KEDA (Kafka lag-based autoscaling), Cluster Autoscaler vs. Karpenter for node provisioning speed (Karpenter is faster — sub-minute). Discuss pod disruption budgets, pre-warming via scheduled scaling jobs, and topology spread constraints for AZ resiliency. Address the cold-start problem for JVM services (GraalVM native image, ahead-of-time compilation). Mention graceful shutdown in Kafka consumers (drain in-flight, commit offsets) and why terminationGracePeriodSeconds needs to be tuned. On AWS: Spot instances for stateless consumers with on-demand fallback.
KubernetesKarpenterKEDAAuto-scaling
Walk me through your approach to multi-region active-active or active-passive architecture on AWS for a financial-grade trading platform. Hints
Key angles to hit
Discuss why true active-active is hard for trading (conflicting writes, distributed locking). Preference for active-passive with fast failover for the order book / settlement core, active-active for read-heavy services (odds display, user profiles). Cover Aurora Global Database (sub-second replication, 1-minute failover), MSK (Amazon Kafka) cross-region replication, and Route 53 health checks + ARC (Application Recovery Controller) for traffic steering. Mention RTO/RPO targets and how you'd test them (chaos engineering, GameDays).

05 Kotlin / Java & Code Quality Language
How do you leverage Kotlin coroutines in a high-throughput Kafka consumer to maximize CPU utilization without causing GC pressure or thread starvation? Hints
Key angles to hit
Discuss structured concurrency with coroutine scopes, using Dispatchers.IO for blocking DB calls vs. Dispatchers.Default for CPU-bound work. Cover Flow for back-pressure on the consumer side (conflated channels for latest-value semantics, buffered channels for burst absorption). Mention the JVM GC interaction: short-lived coroutines create allocation pressure — use object pooling for frequently allocated objects, tune G1GC or ZGC for latency-sensitive paths. Address the Kafka consumer's single-threaded poll loop and how to safely parallelize processing while maintaining per-partition ordering guarantees.

06 Observability & Resilience Operations
Why this matters here: Prediction markets are real-time, money-on-the-line systems. Your observability story must go beyond "we have dashboards." Show how instrumentation drives incident response, capacity planning, and architectural decisions.
What does "production-grade observability" look like for an event-driven trading platform? How does it differ from typical microservices observability? Hints
Key angles to hit
Go beyond the three pillars. For event-driven: event lineage tracing (W3C Trace Context propagated through Kafka headers, correlation IDs through the entire chain), consumer lag as a primary SLI (not just service latency), and dead letter queue monitoring as a leading indicator of schema drift or downstream failures. Discuss business-level metrics: trade submission rate, settlement latency, odds freshness — not just CPU/memory. Mention SLO-based alerting (burn rate alerts on error budgets) vs. threshold alerts. For Fanatics specifically: market-level health dashboards that an on-call can read in 10 seconds.

How do you design for resilience in a system where a single bad event (corrupted message, schema mismatch) could cascade and take down the entire pipeline? Hints
Key angles to hit
Cover Schema Registry enforcement at producer level (reject incompatible schemas), poison pill handling (per-record try/catch, route failures to DLQ with full metadata), and circuit breakers (Resilience4j) on downstream calls within consumers. Discuss bulkhead patterns — separate consumer groups for critical vs. non-critical processing paths so a slow settlement service doesn't starve the live-odds pipeline. Mention chaos engineering (Chaos Monkey, fault injection in staging) as a mechanism for validating resilience claims before events like the Super Bowl.

08 Prediction Markets Domain Domain
What are the unique technical challenges of a prediction market vs. a traditional sportsbook, and how would you architect around them? Hints
Key angles to hit
Prediction markets have dynamic pricing (market-maker or AMM-style) vs. fixed odds in traditional sports betting — prices move based on trade flow. Key technical challenges: order matching engine (FIFO, pro-rata, or AMM?), real-time position management (track exposure per user per outcome), and settlement correctness (what happens when an oracle provides wrong data?). Discuss the liquidity problem (thin markets have high spread, need a market-maker or liquidity provider subsystem). Show domain curiosity even if you don't have direct experience.
Domain KnowledgeOrder MatchingAMM
How would you design the settlement system for a prediction market — ensuring correctness, handling disputed outcomes, and maintaining an audit trail? Hints
Key angles to hit
Settlement is the highest-stakes operation. Cover: oracle ingestion pipeline (multiple data sources, consensus/quorum for disputed events), two-phase settlement (pre-settle to lock positions, final settle to distribute funds), and idempotent settlement processing (retry-safe, no double payouts). Audit trail: immutable append-only ledger (event sourced), every state transition logged with actor + timestamp. Discuss the error recovery path: what if settlement fires partially before a crash? How do you detect and resume without duplicating payouts?
