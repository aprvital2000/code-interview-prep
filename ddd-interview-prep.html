Domain-Driven Design Fundamentals

What's the difference between an Entity and a Value Object? Give practical examples.

Entities have identity that persists over time and through changes. Two entities with the same attributes are still distinct if they have different identities. Value Objects have no identity - they're defined entirely by their attributes, and two value objects with identical attributes are interchangeable.

Examples:

  • Entity: A Person with ID 12345. If they change their name from "John Smith" to "John Brown," they're still the same person. Identity matters.
  • Value Object: An Address like "123 Main St, Springfield." If two orders ship to identical addresses, those Address objects are equivalent and interchangeable. A Money object of "$50 USD" - any $50 USD is the same as any other.

Practically: Entities need tracking, versioning, and persistence strategies that maintain identity. Value Objects should be immutable - if you need to change an address, you create a new Address object. This simplifies reasoning and enables safe sharing.

Explain Aggregates and why they matter. How do you identify aggregate boundaries?

An Aggregate is a cluster of entities and value objects treated as a single unit for data changes. It has a root Entity (the Aggregate Root) that's the only entry point for modifications and the only object others can hold references to.

Why they matter:

  • Consistency boundaries: Invariants are enforced within the aggregate, not across aggregates
  • Transaction boundaries: Changes to an aggregate happen in a single transaction
  • Concurrency control: You lock at the aggregate level
  • Simplify design: External objects can't reach in and corrupt internal state

Identifying boundaries:

Start with invariants: What business rules must always be true? If "total order amount must equal sum of line items," Order and OrderLineItems belong in the same aggregate.

Consider lifecycle: Things created, modified, and deleted together likely belong together. An Order and its LineItems have coupled lifecycles.

Keep aggregates small: Only include what's absolutely necessary for consistency. Don't include Customer in the Order aggregate just because they're related - reference by ID instead.

Think transactional: What actually needs to change atomically? Order status and line items, yes. Customer loyalty points, no - that can be eventually consistent.

Example:
// Order Aggregate class Order { // Aggregate Root OrderId id; CustomerId customerId; // Reference, not embedded List<OrderLineItem> lineItems; // Internal entities OrderStatus status; Money totalAmount; void addLineItem(Product product, Quantity qty) { // Enforce invariant: recalculate total lineItems.add(new OrderLineItem(product, qty)); recalculateTotal(); } // Only Order can modify its line items }

Common mistakes: Making aggregates too large (including everything related), allowing external modification of internal entities, trying to maintain cross-aggregate invariants in a single transaction.

What is the Ubiquitous Language and how do you maintain it?

Ubiquitous Language is the shared vocabulary between domain experts and developers that's used consistently in code, conversations, documentation, and tests. It's not developer jargon translated to business terms or vice versa - it's a single language everyone uses.

How to establish it:

Discovery through conversation: Pay attention when domain experts explain concepts. If they say "underwriting" don't translate it to "risk assessment" in your code - use "underwriting."

Model it explicitly: Create a glossary that's actively maintained. When terms are ambiguous, clarify and document the decision.

Enforce in code: Class names, method names, variable names should use domain terms exactly. Not processRequest() but underwritePolicy().

Use in tests: Test names should read like business scenarios: when_policy_expires_coverage_ends() not test_case_47().

Maintaining it:

Regular modeling sessions where language evolves as understanding deepens. Refactor code when you discover better terms. Call out violations in code reviews when technical jargon creeps in. Update documentation immediately when terms change.

Example of language evolution:
Initially: "Users can submit claims"
After learning: "Policyholders file claims, Adjusters assess claims, Claims Managers approve settlements"

The code should reflect this precision - not a generic User class but Policyholder, Adjuster, ClaimsManager each with appropriate behaviors.
Explain Bounded Contexts and Context Mapping patterns.

A Bounded Context is an explicit boundary within which a particular domain model is defined and applicable. Same terms can mean different things in different contexts, and that's okay - each context has its own model optimized for its needs.

Context Mapping Patterns:

Shared Kernel

Two contexts share a subset of the domain model. They must coordinate changes. Use sparingly - creates coupling.

Example: Order and Billing contexts share a core set of Customer data structures

Customer-Supplier

Downstream context (customer) depends on upstream (supplier), but supplier has some obligation to support customer needs.

Example: Reporting context (customer) depends on Sales context (supplier) - sales team considers reporting needs but owns the model

Conformist

Downstream fully conforms to upstream's model with no negotiation power.

Example: Your system consuming a third-party payment API - you adapt to their model

Anticorruption Layer (ACL)

Downstream creates a translation layer to protect its model from upstream's influence.

Example: Modern microservice wrapping a legacy system, translating its outdated concepts to clean domain model

Open Host Service

Upstream defines a protocol/API designed to serve multiple downstream consumers.

Example: Product Catalog service exposing a well-documented REST API for multiple consuming contexts

Published Language

A well-documented shared language for integration, often using industry standards.

Example: Using FHIR standard for healthcare data exchange between contexts

Separate Ways

Contexts have no connection - explicitly deciding integration isn't worth it.

Example: Internal HR system and customer-facing e-commerce have no shared concepts

Partnership

Two contexts succeed or fail together, requiring coordinated evolution.

Example: Frontend and Backend teams collaborating closely on a new feature

Practical example:
Sales Context -> (Customer-Supplier) -> Fulfillment Context ↓ (ACL) Legacy Warehouse System

Sales defines Customer with sales attributes, Fulfillment has its own Customer focused on shipping details, and an ACL translates to the legacy warehouse's antiquated data format.

What are Domain Events and how do they differ from regular events?

Domain Events represent something significant that happened in the domain, expressed in past tense using ubiquitous language. They're first-class domain concepts that domain experts care about, not technical infrastructure events.

Characteristics:

  • Business significance: "OrderPlaced", "PaymentReceived", "PolicyExpired" - things the business tracks and cares about
  • Immutable: They represent historical facts that can't be changed
  • Self-contained: Include all relevant information someone would need to react to the event
  • Named in past tense: "CustomerRelocated" not "CustomerRelocating" or "RelocateCustomer"

Difference from regular events:

Domain Events are part of your domain model and appear in conversations with domain experts. Technical events like "DatabaseConnectionLost" or "CacheInvalidated" are infrastructure concerns.

Domain Events often trigger business processes. "PaymentReceived" might trigger "SendReceipt" and "UpdateInventory" - these are domain policies. Technical events trigger technical responses.

Usage patterns:

Within a bounded context:

Coordinate between aggregates without tight coupling

class Order { void complete() { this.status = COMPLETED; raiseEvent(new OrderCompleted(orderId, customerId, totalAmount)); } } // Elsewhere in same context on(OrderCompleted event) { loyaltyService.awardPoints(event.customerId, event.totalAmount); }

Between bounded contexts:

Integrate loosely via event-driven architecture

  • Order context publishes "OrderPlaced"
  • Inventory context subscribes and reserves stock
  • Shipping context subscribes and creates shipment

Event Sourcing:

Store domain events as source of truth instead of current state

Benefits: Decoupling, auditability, temporal queries ("what was the state last Tuesday?"), business process visibility, enabling reactive architectures.

Event Storming

Walk me through facilitating an Event Storming session for a new feature. What are the steps?

Here's how I'd run a Process-Level Event Storming for a new feature:

Pre-session (30 mins):

  • Book a room with a very long wall (8+ meters) or large table space
  • Get unlimited orange, blue, yellow, purple, pink sticky notes and thick markers
  • Invite domain experts, developers, QA, product owner - 6-12 people max
  • Prepare a simple scope statement: "We're exploring the returns process from customer initiation to refund completion"

Session Opening (15 mins):

  • Explain the color coding briefly - don't overwhelm with theory
  • Emphasize: no idea is wrong, we're discovering together, park technical solutions for now
  • State the scope clearly: "Start when customer clicks 'Return Item', end when money is back in their account"

Phase 1: Event Storm (30-45 mins)

  • Everyone silently writes domain events (orange stickies) in past tense
  • Place them on the wall in rough chronological order
  • No discussion yet - just rapid brain dump
  • I participate but don't dominate - let domain experts lead
  • Call time when flow slows

Phase 2: Timeline Enforcement (30-45 mins)

  • Walk the timeline left to right as a group
  • Reorganize events into correct sequence
  • This is where conflicting mental models surface - "Wait, we check inventory before or after payment?"
  • Mark hot spots (pink) for unresolved questions
  • Note duplicates or different words for same event

Phase 3: Add Commands (20-30 mins)

  • For each event, ask "What triggered this?"
  • Add blue stickies above the events: "Submit Return Request", "Approve Return"
  • Identify who performs each command (small yellow stickies for actors)

Phase 4: Identify Policies (15-20 mins)

  • Look for "whenever X happens, then Y" patterns
  • Purple stickies: "Whenever Return Approved, then Notify Warehouse"
  • These often reveal automation opportunities

Phase 5: Find Aggregates (20-30 mins)

  • Group related commands and events
  • Yellow stickies for key concepts: "Return Request", "Refund", "Inventory Adjustment"
  • Ask: what enforces the rules? What changes together?

Phase 6: Spot Boundaries (15-20 mins)

  • Look for natural breaks in the flow
  • Where do we "hand off" to another team/system?
  • Different terminology emerging? Different experts becoming relevant?
  • These suggest bounded context boundaries

Wrap-up (15 mins)

  • Summarize key discoveries and unresolved questions
  • Take photos of the wall from multiple angles
  • Assign owners to pink sticky hot spots
  • Schedule follow-up if needed

Post-session:

  • Document insights, not every sticky
  • Create a simple diagram of discovered bounded contexts
  • Share with team and stakeholders
  • Use output to guide architectural decisions

Facilitation tips:

  • Keep energy high - stand, move around
  • Redirect technical rabbit holes: "Great point, let's capture that but stay on the domain for now"
  • Draw out quiet participants: "Sarah, you handle returns daily - what are we missing?"
  • When conflict arises, mark it as a hot spot and keep moving
  • Watch for fatigue after 90 mins - take breaks

Red flags during session:

  • Domain experts are silent - you invited the wrong people
  • Everything is a hot spot - scope is too broad, narrow it down
  • No disagreements - people aren't engaged or one person is dominating
  • Too many technical terms - refocus on business events
How do you handle conflicting views during Event Storming?

Conflicts are actually a feature, not a bug - they surface hidden assumptions that would have become bugs later. Here's how I handle them:

Acknowledge the value immediately:

"This is exactly the kind of thing we need to discover now, not in production. Let's dig in."

Make it visible:

  • Put both viewpoints on the wall with pink hot spot stickies
  • Don't try to resolve immediately if it's blocking flow
  • Note the people involved so we can dive deeper later

Investigate the source:

Different parts of the business?

"Sarah, you work in the Chicago warehouse. Tom, you're in Atlanta. Are returns actually handled differently between locations?"

→ Might reveal process variance that needs harmonizing or legitimate context boundaries

Different time periods?

"Is this how we do it today, or how we used to do it? Or how we want to do it?"

→ Distinguish current state, legacy process, and future vision

Different edge cases?

"Are we talking about in-store returns vs online returns?"

→ Might need separate flows or conditional logic

Different roles' perspectives?

"Customer service sees it this way, but warehouse sees it differently - what actually happens?"

→ Need to trace the actual process, not assumed process

Resolution techniques:

Check the receipts:

"Can we pull up the system and see what actually happens?" or "Let's look at the last few returns in the logs"

Real data beats opinions

Follow the money/inventory/paper trail:

"Walk me through: physical item arrives at warehouse, then what? And what updates in the system?"

Timebox investigation:

"Let's spend 10 minutes on this now. If we can't resolve it, we'll schedule a deep dive with operations."

Create parallel flows:

If it's genuinely two different processes, map both flows and note where they diverge

Escalate if needed:

"This seems like a policy decision above our level. Let's document both options and get a ruling from [stakeholder]."

Example from real session:

Conflict: Half the team said "Refund Issued" happens immediately after "Return Approved." Other half said it happens after "Item Inspected."

Investigation:
  • Asked warehouse rep to describe physical process
  • Discovered: Policy says refund after approval, but warehouse often finds damaged items during inspection
  • This meant refunds were being issued then reversed - causing customer service issues
Resolution:
  • Mapped the actual flow: Return Approved → Item Inspected → Inspection Passed/Failed → Refund Issued or Return Rejected
  • Added policy: "Whenever Inspection Failed, then Notify Customer Service"
  • Revealed a bounded context boundary: Returns Processing vs Refund Management
  • Led to decision: Change policy to refund only after inspection

What NOT to do:

  • Let the loudest voice win without investigation
  • Steamroll to keep moving - conflicts signal important complexity
  • Defer everything - some questions need answers now
  • Let it devolve into technical solution debates - stay at the domain level

Documentation: Capture both the conflict and resolution: "Initially we thought X, but discovered Y, so the actual flow is Z." This context is valuable for future team members.

What anti-patterns have you seen in Event Storming sessions?

Here are the most common ways Event Storming goes wrong:

1. CRUD-Storming

What it looks like: Events named "Customer Created", "Customer Updated", "Customer Deleted", "Order Created", "Order Updated"...

Why it's wrong: These aren't domain events, they're database operations. You learn nothing about the actual business.

Fix: Ask "Why was it created? What happened in the business?" Get to "Customer Registered", "Customer Relocated", "Order Placed", "Order Cancelled"

2. Solution Storming

What it looks like: 30 minutes in, people are debating microservices architecture, database schemas, message queues

Why it's wrong: You're designing solutions before understanding the problem. Technical concerns derail domain exploration.

Fix: "Great technical point - let's capture it and come back after we understand the domain. Right now, what happens in the business?"

3. Waterfall Event Storming

What it looks like: Facilitator at the board, calling on people one by one to contribute events while others watch

Why it's wrong: You lose the parallel exploration and emergent patterns. It becomes sequential requirements gathering.

Fix: Enforce the chaotic storm phase. Everyone posts simultaneously. No discussion during initial brain dump.

4. The Academic Abstract

What it looks like: Events are generic and philosophical: "State Changed", "Business Process Initiated", "Validation Occurred"

Why it's wrong: Too abstract to be useful. Domain experts check out because they don't recognize their world.

Fix: Push for concrete, specific events in domain language. Not "Transaction Processed" but "Payment Authorized" or "Wire Transfer Completed"

5. Analysis Paralysis on Colors

What it looks like: "Is this an aggregate or a read model? Should this be purple or lilac? Is this a command or a domain event?"

Why it's wrong: Theoretical purity blocks progress. The taxonomy matters less than capturing the knowledge.

Fix: "Close enough - let's keep moving. We can refine later if needed."

6. Missing the Domain Experts

What it looks like: Room full of developers, architects, maybe a product manager. No one who actually does the work daily.

Why it's wrong: You get speculative events based on assumptions, not reality. Critical edge cases and nuances are missed.

Fix: Don't schedule until you have the right people. One expert who processes returns daily is worth five developers guessing.

7. Scope Explosion

What it looks like: Started with "new returns feature", now mapping the entire e-commerce platform history

Why it's wrong: Takes too long, creates fatigue, loses detail where it matters

Fix: Ruthlessly enforce boundaries. "That's important but out of scope - let's note it for a different session."

8. Hot Spot Hoarding

What it looks like: Every third sticky is pink. Everything is a question or problem.

Why it's wrong: Suggests scope is too ambitious or wrong people in room. Too many open questions paralyzes next steps.

Fix: Narrow scope or get more knowledgeable participants. Some hot spots are normal; majority hot spots means you're not ready.

9. Silent Documentation

What it looks like: Facilitator says they'll "write this up" after. Nothing gets captured in real-time.

Why it's wrong: Context and nuance get lost. Decisions made and alternatives considered disappear.

Fix: Assign someone to photograph the wall every 20-30 minutes. Capture key decisions and conflicts immediately in a shared doc.

10. No Follow-Through

What it looks like: Great session, lots of energy, photos taken... then nothing happens. No decisions made, no code changes, no process improvements.

Why it's wrong: Wastes everyone's time. Domain experts won't participate again.

Fix: End session with clear actions and owners. Schedule follow-up. Show results - "We implemented bounded contexts based on our session."

11. The Monologue

What it looks like: One person (often senior dev or architect) explaining their mental model while others add sticky notes dutifully

Why it's wrong: You get one perspective, not emergent shared understanding. Group wisdom is lost.

Fix: "Thanks for that insight - let's capture it. Now, does anyone see it differently?" Actively solicit dissent.

12. Tool Fetishism

What it looks like: "Can we do this in Miro/Figma/specialized Event Storming software?"

Why it's wrong: Digital tools slow things down, create barriers to spontaneous contribution, and reduce spatial awareness

Fix: Physical wall with sticky notes for the main session. Digitize afterward if needed, but don't sacrifice the dynamic energy of physical collaboration.

Microservices Decomposition

What principles guide your microservice decomposition strategy?

I use multiple complementary principles, not just one approach:

1. Business Capability Alignment

Decompose around what the business does, not how software is structured. Each service owns a complete capability.

Examples:

  • Product Catalog (manage products, categories, attributes)
  • Order Management (place, track, modify orders)
  • Inventory (stock levels, reservations, replenishment)
  • Pricing (calculate prices, manage promotions, discounts)

Not: DatabaseService, UIService, LogicService - these are technical layers, not capabilities.

2. Bounded Context Boundaries

Services should align with DDD bounded contexts. Each service has its own domain model and ubiquitous language.

The "Customer" in Sales service is different from "Customer" in Support service - distinct models, distinct databases, distinct teams.

3. Single Responsibility Principle

A service should have one reason to change. If promotions rules change, only the Pricing service updates. If shipping logic changes, only the Fulfillment service updates.

4. Independent Deployability

You should be able to deploy a service without coordinating with other teams. This implies:

  • No shared databases
  • Versioned APIs
  • Backward compatibility or consumer-driven contracts

5. Data Ownership

Each service exclusively owns its data. No other service writes directly to another's database. If Service A needs data from Service B, it calls B's API or subscribes to B's events.

6. Team Autonomy

Conway's Law: System design mirrors communication structure. Design services around team boundaries - a service should be fully owned by one team (though a team might own multiple services).

7. Change Frequency Alignment

Group things that change together. Separate things that change at different rates. Pricing algorithms change weekly; product catalog structure changes quarterly; customer contact info changes constantly - these belong in different services.

8. Scale Independently

Parts of the system with different scaling needs should be separate services. Product browsing might need 100x more capacity than checkout.

9. Technology Diversity Where It Adds Value

Allow different tech stacks when there's a genuine benefit. Search might use Elasticsearch, recommendations might use Python/ML, order processing might use Java/Spring. But don't create diversity for its own sake.

10. Resilience Boundaries

Failures should be isolated. Critical path (checkout) separate from nice-to-have (recommendations). If recommendations crash, checkout keeps working.

Practical Example - E-commerce decomposition:
Product Catalog Service - Owns: products, categories, attributes, images - Why: Catalog structure changes separately from pricing - Team: Content Management Pricing Service - Owns: base prices, promotions, discount rules - Why: Pricing logic changes frequently, needs different expertise - Team: Revenue Optimization Inventory Service - Owns: stock levels, reservations, warehouses - Why: Real-time stock is high-contention; needs specialized scaling - Team: Operations Order Service - Owns: orders, order items, order status - Why: Core transaction boundary; different lifecycle from fulfillment - Team: Order Management Payment Service - Owns: payment methods, transactions, refunds - Why: Security isolation, PCI compliance, specialized team - Team: Payments/Compliance Fulfillment Service - Owns: shipments, tracking, carriers - Why: Integrates with shipping partners, changes independently - Team: Logistics

Anti-patterns to avoid:

  • Anemic services: CRUD wrappers around database tables with no business logic
  • Distributed monolith: Services so tightly coupled they can't deploy independently - you've just made your monolith slower
  • Data-driven decomposition: Splitting by database tables rather than business capabilities
  • Too fine-grained: 100 nano-services that do almost nothing - coordination overhead kills you

How I validate decomposition:

  • Can you explain each service to a business person in one sentence using their language?
  • Can services deploy independently?
  • Does each service have a clear team owner?
  • Do most business changes affect only 1-2 services?
  • Are cross-service transactions rare?

If yes to these, decomposition is probably sound.

How do you decide whether to split a service or keep it together?

This is the million-dollar question because both extremes are bad - monoliths become unmaintainable, but too many services create operational chaos. Here's my decision framework:

Signals to SPLIT:

1. Different change velocities

Service A's functionality changes weekly, Service B's changes quarterly → Split them so B's stability isn't threatened by A's churn.

Example: Product recommendations (constant ML model updates) vs Product catalog structure (stable) - even though related, split them.

2. Different scalability needs

One part needs 10x more instances than another.

Example: Read-heavy product browsing vs write-heavy checkout - browse might need 50 instances while checkout needs 5.

3. Different availability requirements

Core functionality needs 99.99% uptime, peripheral features can tolerate 99.9%.

Example: Payment processing (critical) vs Product reviews (nice-to-have) - isolate so reviews outage doesn't risk payments.

4. Team boundaries and cognitive load

One team can't effectively maintain both areas because they require different expertise.

Example: Fraud detection (ML/data science expertise) vs Order management (business logic expertise) - different mental models, different specialists.

5. Different data access patterns

One needs strong consistency, another prefers eventual consistency.

Example: Inventory (real-time strong consistency to prevent oversells) vs Search index (eventual consistency acceptable) - different database needs.

6. Security/compliance isolation

PCI, HIPAA, GDPR might require strong isolation.

Example: Payment data needs strict PCI compliance, separate it from less-sensitive product data to minimize compliance scope.

7. Bounded context boundaries are clear

Distinct ubiquitous languages emerging, concepts mean different things in each area.

Example: "Return" in customer-facing service (return request) vs warehouse service (physical item receipt) - different models, split them.

Signals to KEEP TOGETHER:

1. Constantly changing together

Every feature touches both areas - they're coupled by business logic.

Example: Shopping cart and cart promotions - almost every cart change affects promotion calculations. Splitting creates chatty integration.

2. Same transaction boundary

Strong consistency requirements across both areas.

Example: Order and Order Items must stay consistent - if you split them, you'll need distributed transactions or complex saga patterns. Not worth it.

3. Low complexity, small codebase

Both areas combined are <10K lines of code, single team maintains easily.

Example: Product tagging and product search might seem different, but if they're both simple and managed by catalog team, splitting adds overhead without benefit.

4. Shared domain model

Same entities, same lifecycle, same invariants.

Example: Invoice and Invoice Line Items - these are parts of one aggregate, don't split aggregates across services.

5. Operational overhead not justified

Each service adds: deployment pipeline, monitoring, logging, alerting, documentation, versioning burden.

If you'd create 5 services each doing trivial work, consolidate. The rule of thumb: is the service complex enough to justify its operational overhead?

6. Team is already overwhelmed

Adding more services when team is struggling with existing ones makes things worse.

Start with fewer, well-defined services. Split later when capacity exists.

7. Uncertain boundaries

Still figuring out the domain model - premature decomposition commits you to interfaces that will churn.

Build modularly in a monolith first, extract services when boundaries are clear.

Decision Process - Scorecard approach:

Reasons to Split: [ ] Different change rates (weight: 3) [ ] Different scale needs (weight: 3) [ ] Different teams/expertise (weight: 2) [ ] Clear bounded context (weight: 3) [ ] Different SLAs (weight: 2) [ ] Compliance isolation (weight: 2) Reasons to Keep Together: [ ] Change together frequently (weight: -4) [ ] Same transaction needs (weight: -4) [ ] Low complexity (weight: -2) [ ] Shared lifecycle (weight: -3) [ ] Team bandwidth (weight: -2) [ ] Unclear boundaries (weight: -3)

If score > 5, consider splitting. If score < 0, keep together.

Real example decision:

Question: Split "User Profile Service" into "Authentication Service" + "Profile Management Service"?

Analysis:
  • Different change rates: Auth is stable, profiles add fields frequently (+3)
  • Different expertise: Security team owns auth, product team owns profiles (+2)
  • Different SLAs: Auth is critical path, profiles less so (+2)
  • But: Auth often needs profile data for authorization (-2)
  • Operational overhead: Two services, two deployments (-1)
Score: +4 → Borderline. Decision: Start together, revisit when profile complexity grows.

Pragmatic advice:

  • Start with fewer, larger services. It's easier to split later than to merge services once you've built separate teams, schemas, and contracts around them.
  • When in doubt, keep together but maintain clean module boundaries internally so future extraction is easier.
  • Use feature flags to test logical separation before physical separation.
How do you handle cross-service transactions? What patterns do you use?

Cross-service transactions are one of the hardest microservices problems because you lose ACID guarantees. Here's how I approach it:

First Principle: Avoid Them

Seriously. If you're constantly needing distributed transactions, your service boundaries are probably wrong. Redesign toward better-aligned bounded contexts or aggregates that keep transactional consistency within a service.

When You Can't Avoid Them:

Pattern 1: Saga Pattern

A saga is a sequence of local transactions coordinated across services. If any step fails, compensating transactions undo completed steps.

Choreography-based Saga (event-driven):

Order Service: Creates order → publishes OrderCreated ↓ Inventory Service: Reserves stock → publishes StockReserved ↓ Payment Service: Charges card → publishes PaymentCompleted ↓ Shipping Service: Creates shipment → publishes ShipmentCreated If payment fails: Payment Service publishes PaymentFailed ↓ Inventory Service compensates: releases reserved stock ↓ Order Service compensates: cancels order

Pros: Loose coupling, each service autonomous

Cons: Hard to reason about, distributed debugging nightmare, no isolation (partial states visible)

Orchestration-based Saga:

Order Orchestrator: 1. Call Inventory.reserve() 2. If success, call Payment.charge() 3. If success, call Shipping.create() 4. If any fail, call compensations in reverse

Pros: Centralized logic easier to understand, explicit state machine

Cons: Orchestrator becomes coupling point, orchestrator itself is stateful and needs HA

Pattern 2: Two-Phase Commit (2PC)

Coordinator asks all services to prepare (phase 1). If all agree, coordinator tells them to commit (phase 2). If any can't prepare, coordinator tells all to abort.

When I use it: Almost never in distributed systems. It's blocking, scales poorly, and coordinator is single point of failure. Only for rare cases with very few participants in trusted network.

Pattern 3: Event Sourcing + Event-Driven Eventual Consistency

Instead of coordinating synchronously, publish events and let services react asynchronously.

Order placed → Order Service saves and publishes OrderPlaced Inventory Service subscribes: - Receives OrderPlaced - Reserves stock - Publishes StockReserved Payment Service subscribes: - Receives StockReserved - Processes payment - Publishes PaymentSucceeded or PaymentFailed Order Service subscribes: - Receives PaymentSucceeded → marks order confirmed - OR receives PaymentFailed → cancels order Inventory Service subscribes: - Receives PaymentFailed → releases reservation

Pros: Services fully decoupled, natural audit trail, scales well

Cons: Eventual consistency (order is "pending" state briefly), requires idempotency, message ordering challenges

Requirement Pattern
Strong consistency required Reconsider boundaries OR 2PC (rarely)
Eventual consistency acceptable Event-driven sagas (choreography)
Complex workflow logic Orchestrated saga
High throughput, loosely coupled Event sourcing + eventual consistency
Compensation always possible Saga with compensating transactions
Read-heavy cross-service queries CQRS with read replicas

Monitoring & Observability:

Essential for distributed transactions:

  • Correlation IDs across all services
  • Saga state machine tracking (what step failed, how many compensations)
  • Timeout handling (what if Payment service never responds?)
  • Dead letter queues for failed compensations
  • Metrics: saga success rate, compensation rate, average completion time

What NOT to do:

  • Don't use distributed transactions for every operation
  • Don't ignore partial failure states
  • Don't forget timeouts (saga could hang forever)
  • Don't skip idempotency - retries will corrupt data
  • Don't hide eventual consistency from users - show "processing" states in UI

Data Sharing Between Microservices

What are the different patterns for sharing data between microservices? When do you use each?

Data sharing is the core challenge in microservices. Each pattern has trade-offs. Here's my framework:

Pattern 1: API Calls (Synchronous Request-Response)

Service A calls Service B's REST/gRPC API to get data.

When to use:

  • Need current, authoritative data
  • Low latency acceptable (services in same datacenter)
  • Infrequent access (not on every request)
  • Simple data structures

Pros: Always fresh data, simple to understand, strong consistency

Cons: Creates runtime dependency, latency accumulates, can't serve requests if network partitions

Anti-pattern: Calling 5 services to render one page - that's a distributed monolith

Pattern 2: Data Replication (Event-Driven)

Source service publishes change events; consuming services maintain local read replicas.

When to use:

  • High read volume (every order needs customer info)
  • Service needs to function autonomously even if source is down
  • Eventual consistency acceptable
  • Relatively stable data (not changing every second)

Pros: Fast reads (local data), no runtime dependency, service autonomy

Cons: Eventual consistency (replica might lag), storage duplication, schema evolution challenges, complexity of sync logic

Pattern 3: Shared Database (Anti-pattern... mostly)

Multiple services read/write the same database tables.

When to use:

Almost never in true microservices. Only acceptable when:

  • Transitioning from monolith (temporary state)
  • Two services are actually one service that should be merged
  • Read-only shared reference data (lookup tables)

Cons: Defeats entire purpose of microservices - tight coupling, no independent deployment, schema changes affect everyone

Pattern 4: API Composition / Backend for Frontend

An API Gateway or BFF aggregates data from multiple services before responding.

When to use:

  • Frontend needs combined view from multiple services
  • Don't want chatty frontend ↔ backend calls
  • Can tolerate latency of parallel fan-out

Pros: Frontend gets exactly what it needs in one call, encapsulates complexity

Cons: BFF becomes coupling point, increased latency, orchestration complexity

Pattern 5: CQRS with Materialized Views

Separate read models optimized for queries, populated asynchronously from source events.

When to use:

  • Complex queries spanning multiple services
  • Read-heavy workloads
  • Reporting/analytics
  • Query patterns very different from command patterns

Pros: Optimized for reads, no cross-service joins, eventual consistency acceptable for queries

Cons: Complexity of dual models, eventual consistency lag, storage overhead

Pattern 6: Data Ownership with References

Services own their data, reference others by ID only.

When to use:

Default pattern - always own data, reference others by ID

Pros: Clear ownership, loose coupling, independent schemas

Cons: Requires composition or replication for full details

Pattern 7: Event Sourcing for Audit/Replayability

Store all events that change state; services can rebuild state by replaying events.

When to use:

  • Audit trail required
  • Temporal queries ("what was state on Jan 1?")
  • New services need historical data
  • Analytics on event streams

Pros: Complete history, replayable, enables new consumers later

Cons: Complexity, event schema evolution, storage growth

Decision Matrix:

Need Pattern
Always current data, low volume API Calls (Pattern 1)
Fast reads, autonomous service Data Replication (Pattern 2)
Aggregated view for frontend API Composition (Pattern 4)
Complex queries across services CQRS Read Models (Pattern 5)
Audit trail, temporal queries Event Sourcing (Pattern 7)
Clear ownership, loose coupling Reference by ID (Pattern 6)
How do you handle data consistency across services?

Data consistency in microservices is about trade-offs. You can't have strong consistency everywhere without sacrificing availability and partition tolerance (CAP theorem). Here's how I think about it:

Types of Consistency:

  • Strong Consistency: All nodes see the same data at the same time. Read after write returns latest write.
  • Eventual Consistency: All nodes will eventually converge to same state, but might temporarily diverge.
  • Causal Consistency: Causally related operations seen in correct order; unrelated operations might be out of order.

My Framework:

Step 1: Identify Consistency Requirements per Business Operation

Strong consistency required:

  • Financial transactions (payments, refunds)
  • Inventory reservation (can't oversell)
  • Account balance operations
  • Authentication/authorization

Eventual consistency acceptable:

  • Product catalog updates
  • Customer profile changes
  • Search index updates
  • Analytics/reporting
  • Recommendations

Step 2: Choose Pattern Based on Requirement

For Strong Consistency:

Approach A: Keep it in one service

If two things need strong consistency, maybe they belong in same service/aggregate.

Example: Order and OrderLineItems must be consistent → same aggregate, same service, same DB transaction.

Approach B: Distributed Transaction (rarely)

Two-phase commit for critical operations when data must span services.

Example: Transfer money between accounts in different banking services - might justify 2PC despite overhead.

Approach C: Synchronous saga with compensations

Orchestrate calls synchronously, compensate on failure.

Example: Reserve inventory + charge payment in sequence, rollback if either fails.

For Eventual Consistency:

Approach D: Event-driven updates

Publish events, subscribers update asynchronously.

Monitoring: Track replication lag - alert if replica is >1 minute behind.

Step 3: Handle Inconsistency Windows

Even with eventual consistency, design for the gap:

Make inconsistency visible to users:

{ "orderId": 123, "status": "payment_processing", // Not "completed" "message": "We're processing your payment. You'll receive confirmation shortly." }

Idempotency to handle retries:

async function processPayment(orderId, idempotencyKey) { const existing = await paymentRepo.findByIdempotencyKey(idempotencyKey); if (existing) return existing; // Already processed const payment = await chargeCard(...); await paymentRepo.save(payment, idempotencyKey); return payment; }

Step 4: Monitoring & Alerting

Track consistency metrics:

  • Replication lag (event published → replica updated)
  • Compensation rate (% of sagas that needed rollback)
  • Data divergence (how often replicas differ from source)

Alert on anomalies:

  • Lag > SLA (e.g., >5 seconds for critical paths)
  • Compensation rate spike (suggests system issues)
  • Failed event processing (events stuck in DLQ)
Real-World Example: E-commerce Inventory

Problem: Prevent overselling while maintaining performance.
Constraint: Hundreds of customers trying to buy same popular item simultaneously.

My approach:

Strong consistency where it matters:
// Inventory Service - authoritative, strong consistency class InventoryService { async reserve(productId, quantity, orderId) { return await db.transaction(async tx => { const stock = await tx.inventory.findOne( { productId }, { lock: true } ); if (stock.available < quantity) { throw new InsufficientStockError(); } stock.available -= quantity; stock.reserved += quantity; await tx.inventory.update(stock); await tx.reservations.create({ orderId, productId, quantity }); return { reservationId: ... }; }); } }
Eventual consistency for display:
// Product Service maintains denormalized stock counts // Updated via events for fast reads on('inventory.changed', async event => { await productDb.update( { id: event.productId }, { stockCount: event.available } ); }); // UI shows approximate stock <ProductCard stock={product.stockCount} label="~{stock} available" />
Result:
  • Writes go to single authoritative Inventory Service with ACID transactions (no overselling)
  • Reads use eventually-consistent replicas (fast, scalable)
  • UI sets expectations with approximate counts
  • When user clicks "Buy," we call authoritative service which might reject if stale data misled them

The Pragmatic Reality:

Perfect consistency across microservices is impossible without sacrificing everything else. The art is:

  1. Identify what truly needs strong consistency (usually less than you think)
  2. Keep strongly-consistent things in same service/transaction
  3. Accept eventual consistency elsewhere with monitoring and graceful handling
  4. Make inconsistency windows as small and visible as possible

Most consistency "problems" are actually UX problems - users tolerate eventual consistency if you set expectations properly.
