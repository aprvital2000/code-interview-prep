Question 1: Your Kafka cluster is experiencing slow consumer performance, and you notice that consumer rebalances are happening frequently (every few minutes). What could be causing this, and how would you troubleshoot and fix it?

Frequent rebalancing is a common and disruptive operational issue that can severely impact throughput.

Common Causes

1. Consumer Session Timeout

  • Consumer doesn't send heartbeats within session.timeout.ms (default 10s)
  • Kafka assumes consumer is dead and triggers rebalance
  • Often caused by slow message processing blocking the poll loop

2. Poll Interval Exceeded

  • Consumer doesn't call poll() within max.poll.interval.ms (default 5 minutes)
  • Long-running message processing prevents timely polling
  • Kafka kicks out the consumer

3. Network Issues

  • Intermittent connectivity between consumers and brokers
  • High network latency causing heartbeat delays

4. Consumer Group Instability

  • Consumers constantly joining/leaving (deployments, crashes, restarts)
  • Auto-scaling adding/removing consumers too aggressively

Troubleshooting Steps

  1. Check consumer logs for rebalance messages and reasons
  2. Monitor metrics:
    • Rebalance rate and duration
    • Consumer lag per partition
    • Processing time per message
  3. Check GC logs - long GC pauses can prevent heartbeats
  4. Network diagnostics - latency between consumers and brokers

Solutions

For Slow Processing:

# Increase max.poll.interval.ms to allow longer processing
max.poll.interval.ms = 300000  # 5 minutes

# Reduce max.poll.records to process fewer messages per poll
max.poll.records = 100

# Move heavy processing to async worker threads (keep poll loop fast)
# Commit offsets more frequently

For Session Timeouts:

# Increase session.timeout.ms (e.g., from 10s to 30s)
session.timeout.ms = 30000

# Increase heartbeat.interval.ms proportionally
heartbeat.interval.ms = 10000  # Typically session.timeout/3

# Ensure consumer code doesn't block the heartbeat thread

For Infrastructure:

  • Fix network issues or use dedicated networks
  • Tune JVM heap and GC settings
  • Stagger consumer deployments to avoid mass restarts
  • Use static membership (Kafka 2.3+) with group.instance.id to avoid rebalances during rolling restarts

Best Practice Configuration:

session.timeout.ms = 30000  # 30 seconds
heartbeat.interval.ms = 10000  # 10 seconds
max.poll.interval.ms = 300000  # 5 minutes, or higher if needed
max.poll.records = 500  # Or lower for slow processing
Question 2: Your Kafka cluster is running out of disk space. What are the possible causes, and what operational steps would you take both immediately and long-term?

Running out of disk space is a critical operational issue that can cause broker failures and data loss if not handled quickly.

Possible Causes

1. Retention Settings Too High

  • retention.ms or retention.bytes set too generously
  • Topics accumulating more data than expected
  • No cleanup happening due to misconfiguration

2. Log Compaction Not Working

  • Compacted topics aren't actually compacting
  • log.cleaner.enable=false or cleaner threads insufficient
  • Compaction falling behind production rate

3. Unexpected Traffic Surge

  • Producer throughput much higher than anticipated
  • New topics or use cases generating massive data
  • Retry storms or duplicate messages

4. Large Messages

  • Messages exceeding expected size
  • Uncompressed data when compression should be used

5. Replication Overhead

  • High replication factor multiplying storage needs
  • Unnecessary topic replicas

Immediate Actions (Emergency Triage)

1. Identify the Problem:

# Check disk usage per broker
df -h

# Find largest topics/partitions
du -sh /var/lib/kafka/data/* | sort -h

# Check log directories
ls -lh /var/lib/kafka/data/

2. Free Up Space Quickly:

# Reduce retention temporarily on largest topics:
kafka-configs --alter --topic large-topic \
  --add-config retention.ms=3600000  # 1 hour

# Delete unnecessary topics (be careful!)
kafka-topics --delete --topic old-topic

# Trigger manual cleanup:
# Restart brokers (forces segment deletion) - risky but effective
# Or wait for log cleaner to run
⚠️ Critical: Monitor closely - watch disk usage every few minutes, check if cleanup is working, ensure cluster remains stable.

Long-term Solutions

1. Right-size Retention Policies:

# Audit all topics and set appropriate retention
# Different topics need different retention
retention.ms = 604800000  # 7 days for most topics
retention.ms = 86400000   # 1 day for high-volume logs

2. Enable and Tune Log Compaction:

# For changelog/state topics
cleanup.policy=compact

# Increase cleaner threads
log.cleaner.threads=2

# Tune compaction lag
log.cleaner.min.compaction.lag.ms

3. Implement Compression:

# Enable producer compression
compression.type=snappy  # or lz4

# Can reduce storage by 50-80% depending on data
# Balance compression ratio vs CPU usage

4. Add Storage Capacity:

  • Add new brokers and rebalance partitions
  • Add disks to existing brokers (if possible)
  • Move to larger storage volumes

5. Implement Monitoring and Alerting:

  • Alert at 70% disk usage (warning)
  • Alert at 85% disk usage (critical)
  • Track disk growth rate to predict capacity issues
  • Monitor per-topic storage usage

6. Data Tiering (Kafka 2.8+):

  • Use tiered storage to offload old segments to cheaper storage (S3, etc.)
  • Keep recent data on fast local disks
  • Archive old data to object storage

7. Review Message Sizes:

  • Implement message size limits
  • Use references/pointers for large payloads (store in S3, put reference in Kafka)
  • Compress large messages at application level

Configuration Best Practices

# Broker level
log.retention.hours = 168  # 7 days default
log.segment.bytes = 1073741824  # 1GB segments
log.retention.check.interval.ms = 300000  # Check every 5 min
log.cleaner.enable = true
log.cleaner.threads = 2

# Topic level (override as needed)
retention.ms = 604800000  # Per topic
compression.type = producer  # Honor producer compression
Question 3: After a broker crashes and restarts, you notice under-replicated partitions that aren't recovering. What could be wrong, and how do you diagnose and fix it?

Under-replicated partitions (URPs) mean some partitions don't have all their replicas in-sync, which is a serious availability and durability risk. When they persist after a broker restart, it indicates a deeper problem.

Possible Causes

1. Broker Struggling to Catch Up

  • Follower replica is lagging too far behind the leader
  • Network bandwidth insufficient for replication
  • Disk I/O bottleneck on the follower broker
  • High CPU usage preventing replication threads from working

2. Network Issues

  • Connectivity problems between leader and follower brokers
  • Packet loss or high latency
  • Network partitions or firewall issues
  • DNS resolution problems

3. ISR Configuration Too Strict

  • replica.lag.time.max.ms set too low (replicas dropped from ISR too quickly)
  • replica.fetch.max.bytes too small for large messages
  • Not enough replication threads

4. Disk Failures

  • Disk corruption on the follower broker
  • I/O errors preventing writes
  • Disk full (even after restart)

5. Resource Exhaustion

  • Broker out of memory (OOM)
  • Too many file descriptors open
  • Thread pool exhaustion

6. Data Corruption

  • Log segments corrupted and need recovery
  • Index files corrupted
  • Unclean shutdown left inconsistent state

Diagnosis Steps

1. Identify Under-Replicated Partitions:

# Check cluster status
kafka-topics --bootstrap-server localhost:9092 --describe --under-replicated-partitions

# Check specific topic
kafka-topics --bootstrap-server localhost:9092 --describe --topic my-topic

# Look for partitions where Replicas != Isr (In-Sync Replicas)

2. Check Broker Logs:

# Look for replication errors
grep -i "replica" /var/log/kafka/server.log
grep -i "ISR" /var/log/kafka/server.log
grep -i "error" /var/log/kafka/server.log

# Common error patterns:
# - "Replica fetch failed"
# - "IOException"
# - "NotLeaderForPartitionException"
# - "Broker not alive"

3. Check Broker Health:

# Disk space
df -h

# Disk I/O
iostat -x 5

# Network connectivity
ping <other-broker-ip>
telnet <other-broker-ip> 9092

# CPU and memory
top
free -h

# Check if broker is in cluster
kafka-broker-api-versions --bootstrap-server localhost:9092

Solutions

For Slow Replication/Catch-up:

1. Increase replication capacity:

# In server.properties
num.replica.fetchers = 4  # Increase from default 1
replica.fetch.max.bytes = 10485760  # 10MB, larger if needed
replica.socket.receive.buffer.bytes = 1048576  # 1MB

2. Give more time for replicas to catch up:

replica.lag.time.max.ms = 30000  # Increase from 10s to 30s

3. Throttle replication to avoid overwhelming the broker:

# Set replication throttle (bytes/sec)
kafka-configs --bootstrap-server localhost:9092 --alter \
  --entity-type brokers --entity-name 1 \
  --add-config follower.replication.throttled.rate=10000000

# Remove throttle after catch-up
kafka-configs --bootstrap-server localhost:9092 --alter \
  --entity-type brokers --entity-name 1 \
  --delete-config follower.replication.throttled.rate

For Network Issues:

1. Fix connectivity:

  • Check firewall rules
  • Verify DNS resolution
  • Test network bandwidth between brokers
  • Check for network misconfigurations

2. Increase timeouts:

replica.socket.timeout.ms = 60000  # Increase if network is slow

For Disk Issues:

1. Check and repair disk:

# Check disk health
smartctl -a /dev/sda

# Check filesystem
fsck /dev/sda1

# Move data to healthy disk if needed

2. Clear space if disk full:

  • Reduce retention on topics
  • Delete old log segments
  • Add storage capacity

For Corrupted Data:

1. Delete corrupted segments:

# Stop broker
# Navigate to partition directory
cd /var/lib/kafka-logs/my-topic-0/

# Delete corrupted segment files
rm corrupted-segment.log
rm corrupted-segment.index

# Rebuild indexes
kafka-run-class kafka.tools.DumpLogSegments --deep-iteration --print-data-log --files *.log

2. Reassign partitions to force rebuild:

# Create reassignment JSON
{
  "version": 1,
  "partitions": [
    {"topic": "my-topic", "partition": 0, "replicas": [1,2,3]}
  ]
}

# Execute reassignment
kafka-reassign-partitions --bootstrap-server localhost:9092 \
  --reassignment-json-file reassignment.json --execute

Preventive Measures

1. Monitoring and Alerting:

Alert on:
  • UnderReplicatedPartitions > 0 for > 5 minutes
  • MaxLag > threshold
  • Broker offline
  • Disk usage > 80%

2. Configuration Tuning:

# Production-ready replication settings
num.replica.fetchers = 4
replica.lag.time.max.ms = 30000
replica.fetch.max.bytes = 10485760
replica.socket.timeout.ms = 60000
controlled.shutdown.enable = true
controlled.shutdown.max.retries = 3
unclean.leader.election.enable = false  # Keep false for safety
Question 4: You're experiencing message loss in production. Producers claim they sent messages, but consumers never receive them. How do you investigate and prevent this?

Message loss is one of the most critical operational issues in Kafka. It can be caused by producer, broker, or consumer problems. Systematic investigation is essential.

Possible Causes

Producer-side Issues:

  1. Fire-and-forget sending without checking acknowledgments
  2. Insufficient acks setting (acks=0 or acks=1)
  3. Producer not waiting for send completion
  4. Retries disabled or exhausted
  5. Producer buffer overflow (messages dropped when buffer full)
  6. Network failures without proper error handling

Broker-side Issues:

  1. Unclean leader election (data loss during failover)
  2. Insufficient replication (min.insync.replicas too low)
  3. Broker crashes before data replicated
  4. Log corruption or disk failures
  5. Retention policy deleting data too quickly
  6. Log segments deleted before consumer reads

Consumer-side Issues:

  1. Consumer reading old offsets (data already deleted by retention)
  2. Auto-offset-reset set to 'latest' missing earlier messages
  3. Consumer committing offsets incorrectly
  4. Processing messages but not actually "consuming" them (application bug)

Investigation Steps

1. Verify Messages Were Actually Produced:

# Check topic metrics
kafka-run-class kafka.tools.GetOffsetShell \
  --broker-list localhost:9092 \
  --topic my-topic

# Expected output shows log-end-offset for each partition
# my-topic:0:12345 means partition 0 has 12345 messages

# Read directly from topic to verify messages exist
kafka-console-consumer --bootstrap-server localhost:9092 \
  --topic my-topic \
  --from-beginning \
  --max-messages 10

# Check specific offset range
kafka-console-consumer --bootstrap-server localhost:9092 \
  --topic my-topic \
  --partition 0 \
  --offset 1000 \
  --max-messages 100

2. Check Producer Metrics and Logs:

# Producer application logs - look for:
# - Send failures
# - TimeoutException
# - BufferExhaustedException
# - RecordTooLargeException

# JMX metrics to check:
kafka.producer:type=producer-metrics,client-id=*
  - record-send-rate
  - record-error-rate
  - request-latency-avg
  - buffer-available-bytes

3. Check Broker Logs:

# Look for errors around message acceptance
grep -i "error" /var/log/kafka/server.log
grep -i "leader" /var/log/kafka/server.log
grep -i "unclean" /var/log/kafka/server.log

# Check for under-replicated partitions
kafka-topics --bootstrap-server localhost:9092 \
  --describe --under-replicated-partitions

4. Verify Consumer Offset Position:

# Check consumer group lag
kafka-consumer-groups --bootstrap-server localhost:9092 \
  --group my-consumer-group \
  --describe

# Output shows:
# TOPIC  PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
# If CURRENT-OFFSET jumped ahead, messages were skipped

Solutions by Root Cause

Producer-side Fixes:

1. Ensure proper acknowledgment:

// WRONG - fire and forget
producer.send(record);

// CORRECT - wait for acknowledgment
try {
    RecordMetadata metadata = producer.send(record).get();
    // Message confirmed at offset metadata.offset()
} catch (Exception e) {
    // Handle failure - retry, log, alert
}

// BETTER - async with callback
producer.send(record, (metadata, exception) -> {
    if (exception != null) {
        // Log failure, implement retry logic
        logger.error("Send failed", exception);
    }
});

2. Configure for durability:

# Producer configuration for no data loss
acks = all  # Wait for all in-sync replicas
retries = Integer.MAX_VALUE  # Retry forever
max.in.flight.requests.per.connection = 1  # Ordering guarantee
enable.idempotence = true  # Prevent duplicates on retry
compression.type = snappy  # Optional, reduces network load

# Timeouts
delivery.timeout.ms = 120000  # 2 minutes
request.timeout.ms = 30000  # 30 seconds

Broker-side Fixes:

1. Prevent unclean leader election:

# In server.properties - CRITICAL
unclean.leader.election.enable = false  # Never elect out-of-sync leader
min.insync.replicas = 2  # Require at least 2 replicas for acks=all

# Topic level override if needed
kafka-configs --bootstrap-server localhost:9092 \
  --entity-type topics --entity-name critical-topic \
  --alter --add-config min.insync.replicas=2

2. Ensure proper replication:

# Default replication for new topics
default.replication.factor = 3
min.insync.replicas = 2  # At least 2 must acknowledge

# For existing topics
kafka-configs --bootstrap-server localhost:9092 \
  --entity-type topics --entity-name my-topic \
  --alter --add-config min.insync.replicas=2

Consumer-side Fixes:

1. Correct offset management:

# Consumer configuration
enable.auto.commit = false  # Manual control
auto.offset.reset = earliest  # Start from beginning if no offset

# In code - commit only after successful processing
consumer.poll(Duration.ofMillis(100));
for (ConsumerRecord record : records) {
    try {
        process(record);  // Your business logic
        consumer.commitSync();  # Commit after processing
    } catch (Exception e) {
        // Don't commit - will reprocess on restart
        logger.error("Processing failed", e);
    }
}

End-to-End Durability Configuration

Producer:

acks = all
retries = Integer.MAX_VALUE
max.in.flight.requests.per.connection = 5
enable.idempotence = true
compression.type = snappy
delivery.timeout.ms = 120000

Broker:

# Replication
default.replication.factor = 3
min.insync.replicas = 2
unclean.leader.election.enable = false

# Controlled shutdown
controlled.shutdown.enable = true

Consumer:

enable.auto.commit = false
auto.offset.reset = earliest
isolation.level = read_committed  # For transactional producers
⚠️ Critical Copyright Rule:
  • 15+ words from any single source is a SEVERE VIOLATION
  • ONE quote per source MAXIMUM
  • DEFAULT to paraphrasing; quotes should be rare exceptions
  • Never output song lyrics, poems, haikus, or article paragraphs

Prevention Best Practices

  1. Never use fire-and-forget in production
  2. Always use acks=all for critical data
  3. Enable idempotence on producers
  4. Set min.insync.replicas ≥ 2
  5. Disable unclean leader election
  6. Monitor everything - producers, brokers, consumers
  7. Test failure scenarios regularly
  8. Have runbooks for common issues
  9. Implement message tracking for critical flows
  10. Regular audits of configurations
Question 5: Your Kafka cluster is experiencing severe performance degradation - high latency and low throughput. What are the potential bottlenecks, and how do you systematically troubleshoot them?

Performance degradation in Kafka can stem from multiple layers - network, disk I/O, CPU, memory, or configuration issues. Systematic diagnosis is crucial.

Potential Bottlenecks

1. Disk I/O Saturation

  • Slow disks or disk contention
  • Too many partitions on one broker
  • Insufficient IOPS for workload
  • Log segments not being flushed efficiently

2. Network Saturation

  • Network bandwidth exhausted
  • High replication traffic
  • Large messages consuming bandwidth
  • Network misconfiguration or hardware issues

3. CPU Bottleneck

  • Compression/decompression overhead
  • Too many consumer groups
  • Heavy message transformation
  • Inefficient serialization

4. Memory Pressure

  • Insufficient heap size
  • Excessive GC pauses
  • Page cache exhaustion
  • Too many connections

5. Too Many Partitions

  • Metadata overhead
  • File descriptor exhaustion
  • Leader election delays
  • Rebalancing overhead

Systematic Troubleshooting Approach

Step 1: Identify the Symptom Specifics

# Measure current performance
# Producer latency
kafka-producer-perf-test --topic test-topic \
  --num-records 100000 \
  --record-size 1000 \
  --throughput -1 \
  --producer-props bootstrap.servers=localhost:9092

# Consumer throughput
kafka-consumer-perf-test --broker-list localhost:9092 \
  --topic test-topic \
  --messages 100000

# Check end-to-end latency
kafka-run-class kafka.tools.EndToEndLatency \
  localhost:9092 test-topic 10000 1 1000

Step 2: Check Broker-Level Metrics

# CPU usage
top -b -n 1 | grep java
mpstat 1 5

# Memory
free -h
# Check GC logs
grep "GC" /var/log/kafka/gc.log | tail -100

# Disk I/O
iostat -x 5 3
# Look for:
# - %util close to 100% = saturated
# - await > 10ms = slow disks
# - High read/write throughput

# Network
iftop
nethogs
# Check bandwidth utilization

# File descriptors
lsof -p <kafka-pid> | wc -l
ulimit -n

Question 6: You need to upgrade your Kafka cluster from version 2.8 to 3.6 with zero downtime. What's your strategy, and what are the potential pitfalls?

Zero-downtime upgrades are challenging but essential for production systems. Kafka supports rolling upgrades, but careful planning is required.

Upgrade Strategy (Rolling Upgrade)

Phase 1: Pre-upgrade Preparation (1-2 weeks before)

  1. Review release notes thoroughly
    • Breaking changes
    • Deprecated features
    • New features
    • Known issues
  2. Backup everything 
    # Backup broker configurations
cp /opt/kafka/config/server.properties \
   /backup/server.properties.$(date +%Y%m%d)

# Export topic configurations
kafka-topics --bootstrap-server localhost:9092 --describe \
  > /backup/topics-$(date +%Y%m%d).txt

# Export consumer group offsets
kafka-consumer-groups --bootstrap-server localhost:9092 \
  --all-groups --describe \
  > /backup/consumer-groups-$(date +%Y%m%d).txt
  3. Test in staging environment
  4. Verify compatibility
  5. Create rollback plan
  6. Schedule maintenance window

Phase 2: Upgrade Execution

Step 1: Upgrade one broker at a time

# For each broker (start with non-controller):

# 1. Stop broker gracefully
kafka-server-stop.sh

# 2. Install new version
cd /opt
tar -xzf kafka_2.13-3.6.0.tgz
ln -sf kafka_2.13-3.6.0 kafka

# 3. Update configuration if needed
# IMPORTANT: Keep these during rolling upgrade
inter.broker.protocol.version = 2.8
log.message.format.version = 2.8

# 4. Start the upgraded broker
kafka-server-start.sh -daemon config/server.properties

# 5. Monitor startup
tail -f /var/log/kafka/server.log

# 6. Wait 15-30 minutes before next broker
# Ensure no under-replicated partitions

# 7. Repeat for next broker
⚠️ Critical Monitoring During Upgrade: 
# Run these continuously:
watch -n 5 'kafka-topics --bootstrap-server localhost:9092 \
  --describe --under-replicated-partitions | wc -l'

Step 2: Upgrade protocol versions (after all brokers upgraded)

# Once ALL brokers are on 3.6:

# 1. Upgrade inter-broker protocol
# Edit server.properties on each broker
inter.broker.protocol.version = 3.6

# Rolling restart all brokers

# 2. Upgrade message format version (IRREVERSIBLE!)
log.message.format.version = 3.6

# Rolling restart all brokers again

Common Pitfalls and Solutions

Pitfall Solution
Incompatible configurations Check deprecation warnings before upgrade
Forgetting inter.broker.protocol.version ALWAYS keep old protocol version during rolling upgrade
Under-replicated partitions pile up Throttle replication during upgrade
Controller instability Upgrade controller LAST
Client incompatibility Ensure clients are N-2 compatible
ZooKeeper compatibility Check compatibility matrix, upgrade ZK first if needed
Insufficient rollback testing Test rollback in staging BEFORE production
Metrics/monitoring break Update monitoring dashboards BEFORE upgrade

Upgrade Checklist

Pre-upgrade:
  • ☐ Read release notes thoroughly
  • ☐ Backup all configurations
  • ☐ Test in staging environment
  • ☐ Verify client compatibility
  • ☐ Create rollback plan
During upgrade:
  • ☐ Upgrade non-controller brokers first
  • ☐ One broker at a time
  • ☐ Wait for full ISR recovery between brokers
  • ☐ Monitor under-replicated partitions (must be 0)
Post-upgrade:
  • ☐ All brokers on new version
  • ☐ Upgrade inter.broker.protocol.version
  • ☐ Upgrade log.message.format.version
  • ☐ Performance validation
  • ☐ Monitor for 24-48 hours
Question 7: Your consumers are experiencing continuous rebalancing storms - rebalances happening every 30 seconds. Production is severely impacted. How do you diagnose the root cause and stop it immediately?

Rebalancing storms are one of the most disruptive operational issues. They can bring processing to a near halt. Immediate action is required.

What's Happening

Consumers repeatedly join and leave the consumer group, triggering continuous rebalances. During each rebalance:

  • All consumers stop processing
  • Partitions are reassigned
  • Consumers commit their offsets
  • Processing resumes briefly
  • Then another rebalance triggers

Common Root Causes

  1. Session timeout too aggressive
  2. Max poll interval exceeded
  3. Unstable consumer instances
  4. Aggressive auto-scaling
  5. Misconfigured static membership
  6. Network issues
  7. Broker-side issues

Immediate Fixes (Stop the Bleeding)

Fix 1: Increase Timeouts (Emergency Band-Aid)

# In consumer application, immediately deploy with:

# Increase session timeout significantly
session.timeout.ms = 60000  # 60 seconds (from default 10s)

# Increase heartbeat interval proportionally
heartbeat.interval.ms = 20000  # 20 seconds (1/3 of session timeout)

# Increase max poll interval for slow processing
max.poll.interval.ms = 600000  # 10 minutes (from default 5 min)

Fix 2: Reduce Poll Batch Size

# If consumers are taking too long to process messages:
max.poll.records = 100  # Reduce from default 500

Fix 3: Enable Static Membership

# Prevents rebalances on transient failures
group.instance.id = consumer-pod-1  # Use pod name or similar
session.timeout.ms = 45000

Fix 4: Stop Auto-Scaling Immediately

# If using Kubernetes HPA:
kubectl autoscale deployment consumer-app --min=5 --max=5

# Or delete autoscaler temporarily
kubectl delete hpa consumer-app-hpa

Root Cause Analysis Scenarios

Scenario 1: Session Timeout Root Cause

# Check GC logs
tail -100 gc.log | grep "Full GC"
# Long GC pauses (> 5s) will prevent heartbeats

# Solution: Tune JVM
export JAVA_OPTS="-Xms2g -Xmx2g -XX:+UseG1GC -XX:MaxGCPauseMillis=200"

Scenario 2: Max Poll Interval Root Cause

# Processing is too slow
# Solution: Process asynchronously
consumer.poll(Duration.ofMillis(100));
for (ConsumerRecord record : records) {
    executorService.submit(() -> processMessage(record));
}
// Keep poll loop fast!

Scenario 3: Consumer Instability

# Check OOM kills
kubectl describe pod consumer-pod-1 | grep OOM

# Solution: Increase memory limits
resources:
  requests:
    memory: "2Gi"
  limits:
    memory: "4Gi"

Long-term Solutions

1. Proper Timeout Configuration:

# Production-grade consumer settings
session.timeout.ms = 45000  # 45 seconds
heartbeat.interval.ms = 15000  # 15 seconds
max.poll.interval.ms = 600000  # 10 minutes
group.instance.id = ${HOSTNAME}  # Static membership
max.poll.records = 500

2. Separate Poll Loop from Processing:

// CORRECT - async processing
ExecutorService executor = Executors.newFixedThreadPool(10);

Thread pollThread = new Thread(() -> {
    while (true) {
        ConsumerRecords records = consumer.poll(Duration.ofMillis(100));
        for (ConsumerRecord record : records) {
            buffer.put(record);  // Non-blocking queue
        }
    }
});

// Worker threads do heavy lifting

3. Monitoring and Alerting:

# Critical alerts:
# Alert 1: Rebalance frequency
rate(kafka_consumer_group_rebalance_total[5m]) > 0.1

# Alert 2: Rebalance duration
kafka_consumer_group_rebalance_latency_max > 60000

# Alert 3: Consumer lag during rebalance
delta(kafka_consumer_group_lag[5m]) > 10000
Question 8: You're running a multi-datacenter Kafka deployment with MirrorMaker 2 for replication. Replication lag is growing to hours, and the secondary datacenter is falling further behind. How do you diagnose and fix this?

Multi-datacenter replication lag is a critical issue that can impact disaster recovery, compliance, and business continuity.

Common Root Causes

  1. Network bandwidth exhaustion
  2. MirrorMaker 2 under-provisioned
  3. Target cluster bottleneck
  4. Topic configuration mismatch
  5. Consumer lag on source
  6. Connector configuration issues

Diagnosis Steps

Step 1: Measure Current Replication Lag

# Check MirrorMaker 2 lag on source cluster
kafka-consumer-groups --bootstrap-server source-cluster:9092 \
  --group mirrormaker2-cluster \
  --describe

# Look at LAG column
# Large LAG = replication falling behind

Step 2: Check MirrorMaker 2 Health

# MM2 runs as Kafka Connect cluster

# Look for state: "RUNNING"
# Check individual task states

# Check MM2 logs

Step 3: Check Network Between Datacenters

# Bandwidth test

# Latency test
ping -c 100 target-dc-ip

# Packet loss
ping -c 1000 target-dc-ip | grep loss

Solutions by Root Cause

Solution 1: Network Bandwidth Bottleneck

# Enable compression on MM2
curl -X PUT http://mm2-host:8083/connectors/MirrorSourceConnector/config \

    "compression.type": "snappy",

# Increase task parallelism

# Reduce replication factor on target if DR-only

  1. Prioritize critical topics (pause non-critical replication)

Question 9: Your ZooKeeper ensemble becomes unavailable (split-brain or total failure). Your Kafka cluster is still running but degraded. What immediate actions do you take, and how do you prevent/recover from this?

ZooKeeper failure is one of the most critical Kafka operational emergencies. While Kafka brokers can continue serving existing client connections temporarily, the cluster cannot perform essential coordination tasks.

What Happens When ZooKeeper Fails

Immediate Impacts:

  • ❌ No new partition leader elections
  • ❌ No controller election
  • ❌ No metadata updates
  • ❌ No consumer group coordination
  • ❌ No ACL changes
  • ❌ No configuration changes

Services Still Working (Temporarily):

  • ✅ Existing producers/consumers continue working
  • ✅ Data continues flowing on healthy partitions
  • ✅ Brokers serve requests from page cache
  • ✅ Existing leader/follower relationships maintained
⚠️ This is a degraded state - one broker failure could cause cascading outages!

Diagnosis

Step 1: Confirm ZooKeeper is the Problem

# Test ZooKeeper connectivity
echo "ruok" | nc zk1 2181
# Should return "imok"

# Check all ZK nodes
for host in zk1 zk2 zk3; do
  echo "Testing $host"
  echo "ruok" | nc $host 2181
  echo "stat" | nc $host 2181 | grep Mode
done

# Check broker logs
tail -100 /var/log/kafka/server.log | grep -i zookeeper

Step 2: Identify the Failure Type

# Scenario 1: ZooKeeper split-brain
# Multiple nodes think they're leader
echo "stat" | nc zk1 2181 | grep Mode
echo "stat" | nc zk2 2181 | grep Mode
echo "stat" | nc zk3 2181 | grep Mode

# Scenario 2: ZooKeeper quorum lost
# < majority of ZK nodes available

# Scenario 3: Total ZooKeeper failure
# All ZK nodes down

Immediate Actions

Action 1: Don't Panic - Assess Impact First

# Test producer
echo "test message" | kafka-console-producer \
  --bootstrap-server localhost:9092 \
  --topic test-topic

# Test consumer
kafka-console-consumer --bootstrap-server localhost:9092 \
  --topic test-topic --from-beginning --max-messages 1

# If these work, clients are still functioning

Action 2: Stabilize - Prevent Cascading Failures

CRITICAL: Do NOT restart any Kafka brokers!

Without ZooKeeper, broker restarts will fail or cause issues.

  • Put cluster in read-only mode mentally
  • No deployments
  • No configuration changes
  • No broker restarts
  • No topic operations

Action 3: Recover ZooKeeper ASAP

This is the priority - everything else is temporary mitigation.

Recovery Scenarios

Scenario 1: Single ZK Node Failure (Quorum Intact)

# If you have 3 ZK nodes and 1 failed, quorum (2/3) remains
# Fix the failed node:

# 1. Check why it failed
tail -500 /var/zookeeper/logs/zookeeper.log

# 2. Fix root cause (disk, memory, config, network)
df -h
free -h

# 3. Restart ZK node
systemctl restart zookeeper

# 4. Verify it rejoined
echo "stat" | nc zk-node 2181

Scenario 2: ZooKeeper Quorum Lost

# Example: 3-node ensemble, only 1 node up
# Need to restore at least 2 nodes

# Fix and restart downed nodes
systemctl stop zookeeper
# Restore from backup if needed
tar -xzf /backup/zookeeper-data-latest.tar.gz -C /var/zookeeper/
systemctl start zookeeper

# Once 2+ nodes up, quorum restored!

Scenario 3: ZooKeeper Split-brain

# Network partition causing multiple leaders

# 1. Identify legitimate leader
for host in zk1 zk2 zk3; do
  echo "$host:"
  echo "ls /brokers/ids" | zkCli.sh -server $host:2181
done

# 2. Shut down minority partition ZK nodes
systemctl stop zookeeper  # On minority node

# 3. Fix network partition

# 4. Restart minority nodes once network fixed
systemctl start zookeeper

Scenario 4: Total ZooKeeper Failure - Disaster Recovery

# All ZK nodes failed, no backups recoverable
# This is a cluster rebuild scenario

# Step 1: Preserve Kafka data
# DO NOT DELETE KAFKA DATA DIRECTORIES!

# Step 2: Build new ZooKeeper ensemble
# Fresh 3-5 node ZK cluster

# Step 3: Update Kafka broker configs
zookeeper.connect=new-zk1:2181,new-zk2:2181,new-zk3:2181

# Step 4: Restart Kafka brokers ONE AT A TIME
kafka-server-stop.sh
kafka-server-start.sh config/server.properties

# Step 5: Verify metadata recreation
kafka-topics --bootstrap-server localhost:9092 --list

Prevention Strategies

1. Proper ZooKeeper Ensemble Sizing

# Production ZooKeeper configuration
# Use odd number of nodes (3, 5, or 7)
# 3 nodes: tolerates 1 failure
# 5 nodes: tolerates 2 failures (recommended)

# zoo.cfg
tickTime=2000
dataDir=/var/zookeeper/data
dataLogDir=/var/zookeeper/datalog  # Separate disk!
clientPort=2181

server.1=zk1:2888:3888
server.2=zk2:2888:3888
server.3=zk3:2888:3888

# JVM settings
export JVMFLAGS="-Xms4g -Xmx4g -XX:+UseG1GC"

2. ZooKeeper Placement and Isolation

  • Dedicated hardware/VMs for ZooKeeper
  • Don't co-locate ZK with Kafka brokers
  • Spread across failure domains (racks, AZs, DCs)
  • Fast, reliable disks (SSD for transaction logs)
  • Separate disk for dataDir and dataLogDir

3. Monitoring and Alerting

# Critical ZooKeeper metrics:
# 1. ZK ensemble health
for host in zk1 zk2 zk3; do
  echo "ruok" | nc $host 2181 || echo "$host FAILED"
done

# 2. Quorum status
echo "stat" | nc zk1 2181 | grep Mode

# 3. Latency
echo "stat" | nc zk1 2181 | grep Latency

# 4. Disk usage
df -h /var/zookeeper/data

# Alert rules:
- alert: ZooKeeperDown
  expr: up{job="zookeeper"} == 0
  for: 1m

- alert: ZooKeeperQuorumLost
  expr: zookeeper_quorum_size < 2
  for: 1m

4. Regular Backups

# Automated daily backups
# Cron job:
0 2 * * * /opt/scripts/backup-zookeeper.sh

# backup-zookeeper.sh:
#!/bin/bash
DATE=$(date +%Y%m%d-%H%M%S)
BACKUP_DIR=/backup/zookeeper

tar -czf $BACKUP_DIR/zk-data-$DATE.tar.gz /var/zookeeper/data/

# Keep last 30 days
find $BACKUP_DIR -name "zk-data-*.tar.gz" -mtime +30 -delete

# Store off-site
aws s3 sync $BACKUP_DIR s3://my-bucket/zookeeper-backups/

6. Migrate to KRaft (ZooKeeper-less Kafka)

💡 Modern Solution: Kafka 3.3+ supports KRaft mode, eliminating ZooKeeper dependency entirely!
  • No more ZooKeeper operational complexity
  • Faster controller failover
  • Simpler architecture
  • Better scalability

Post-Incident Checklist

  • ☐ Document timeline of ZK failure
  • ☐ Identify root cause
  • ☐ Implement fix to prevent recurrence
  • ☐ Verify ZK ensemble healthy
  • ☐ Verify Kafka cluster fully recovered
  • ☐ Check all brokers registered
  • ☐ Verify controller elected
  • ☐ Check under-replicated partitions (should be 0)
  • ☐ Update runbooks with lessons learned
  • ☐ Consider migrating to KRaft

Critical Reminders

❌ NEVER:
  • Restart Kafka brokers while ZooKeeper is down
  • Restart multiple ZK nodes simultaneously
  • Delete ZK data without backup
  • Ignore ZK alerts
✅ ALWAYS:
  • Maintain ZK quorum (majority of nodes)
  • Have ZK backups
  • Test ZK recovery procedures
  • Monitor ZK health closely
  • Consider migrating to KRaft
