Q 01 How do you approach building reactive microservices with Spring WebFlux, and when would you choose it over traditional Spring MVC? ▼

The core decision is whether the service's workload is I/O-bound or compute-bound. WebFlux shines when a service spends most of its time waiting — waiting on database responses, downstream API calls, or message streams. In those cases, the non-blocking model lets a small thread pool handle far more concurrent requests than a thread-per-request model can sustain under load.

The trade-offs I communicate clearly to teams: reactive code is harder to reason about, harder to debug, and harder to write correctly — especially around error handling and backpressure. So I don't mandate WebFlux everywhere. My rule of thumb: if a service handles high concurrency with significant I/O latency — payment processing callbacks, real-time event streams, API gateway fanouts — WebFlux is the right tool. CRUD-heavy services with simple synchronous flows stay on MVC.

In practice, the most common mistake I see is teams mixing blocking calls into a reactive chain — a JDBC call inside a Mono pipeline, for example. That negates the entire benefit and can deadlock the scheduler. I enforce non-blocking discipline through code review standards and steer teams toward R2DBC for reactive database access rather than trying to wrap JDBC.

Q 02 What are the key patterns you apply when designing reactive APIs with Spring WebFlux for a financial services platform? ▼

Several patterns are non-negotiable in a financial context.

Backpressure handling — consumers must be able to signal capacity limits upstream. I use limitRate() operators and bounded queues on Flux streams to prevent memory exhaustion under load spikes. This is especially important for event-driven endpoints that fan out to multiple downstream services.

Error propagation and recovery — reactive chains need explicit error handling at every layer. I use onErrorResume() for graceful fallbacks and retry() with exponential backoff and jitter for transient failures. In financial flows, I'm explicit about which errors are retryable and which are terminal — a duplicate transaction error should never be retried.

Timeout contracts — every external call in a reactive chain has an explicit timeout() operator. I don't rely on downstream services honoring SLAs; I enforce the timeout on my side and handle it as a defined failure mode.

Context propagation — trace IDs, correlation IDs, and security context need to travel through the reactive chain. Spring's ReactorContext handles this, but it requires deliberate design — I enforce context propagation standards so that distributed traces are complete and audit logs are attributable to the originating request.

Q 03 Walk me through how you would handle exactly-once semantics in a Kafka-based financial transaction pipeline. ▼

Exactly-once in Kafka requires careful design at both the producer and consumer layers. The right framing is: exactly-once delivery is achievable within the Kafka ecosystem, but exactly-once processing requires application-level guarantees as well.

On the producer side, I enable idempotent producers (enable.idempotence=true) and use Kafka transactions when a single business operation needs to write to multiple topics atomically. The transaction API ensures either all writes commit or none do — critical when a payment event needs to be written to both an audit topic and a processing topic simultaneously.

On the consumer side, I use read_committed isolation to only consume committed transactional messages, preventing processing of in-flight or aborted transactions. For processing guarantees, I implement idempotent consumers — every message carries a unique business key, and the consumer checks a deduplication store (typically a Redis or PostgreSQL-backed idempotency table) before processing.

The offset commit strategy matters too. I commit offsets only after successful processing and downstream persistence — never pre-commit. That means a consumer failure reprocesses the last batch, but idempotency at the application layer makes that safe.

In practice I always discuss the performance cost with stakeholders — exactly-once semantics add latency and reduce throughput compared to at-least-once. For high-volume non-financial events I'll often use at-least-once with idempotent consumers, reserving full transactional semantics for payment and settlement flows where the cost of a duplicate is unacceptable.

Q 04 What does a great internal developer platform look like, and how do you build one that engineers actually adopt? ▼

Adoption is the only metric that matters — the most technically elegant platform that engineers route around is a failure. The adoption question has to be answered before the architecture question.

The platforms engineers adopt have three properties: they make the right thing the easy thing, they don't impose ceremony for simple use cases, and they have first-class documentation that respects the engineer's time.

I approach platform builds in three layers. The API layer — well-designed, consistent, versioned REST or event-driven APIs with clear contracts. I invest in OpenAPI spec-first design so the documentation and SDK generation are downstream artifacts of the contract, not afterthoughts. The developer portal — a single place where engineers can discover APIs, access interactive docs, generate client code, and monitor their integration health. I treat this as a product with a product owner, not an infrastructure artifact. The SDK and tooling layer — idiomatic client libraries in the languages teams actually use, with sensible defaults and meaningful error messages.

The adoption flywheel: start with a high-value, high-visibility use case that a prominent internal team actually needs. Build it properly. Let the experience speak. Early adopters become internal advocates, and the platform grows through pull rather than mandate.

Q 05 How do you design APIs for a platform that serves both internal engineers and external partners? ▼

The internal/external distinction drives several key design decisions.

Versioning strategy — external APIs need conservative versioning with long deprecation windows. I use URI versioning (/v1/, /v2/) for external-facing APIs because it's explicit and tooling-friendly. Internally I can use header-based versioning or move faster on breaking changes because I control the consumer teams.

Contract fidelity — external API contracts are commitments. I design external APIs with the most conservative interface possible — minimal required fields, optional extensions, no undocumented behavior. Internal APIs can expose richer, more opinionated contracts because I can coordinate changes across the org.

Authentication and authorization — external APIs use OAuth 2.0 with scoped tokens; the authorization model is explicit and documented. Internal APIs in a zero-trust architecture also use strong auth, but the scope model can be coarser.

Observability asymmetry — external API consumers need visibility into their own usage: rate limit headers, request IDs for support escalation, clear error codes. I expose per-consumer dashboards in the developer portal. At Amex scale specifically, I'd invest early in a unified API gateway handling cross-cutting concerns — auth, rate limiting, logging, routing — so individual microservices don't each implement their own inconsistently.

Q 06 How do you design asynchronous APIs and what are the key trade-offs compared to synchronous REST? ▼

Asynchronous API design is fundamentally about decoupling — the caller doesn't wait for the result, which means the two systems can scale, fail, and evolve independently. That's powerful but it introduces complexity that synchronous APIs hide.

The key design decisions I make explicit upfront: delivery semantics (at-least-once is usually the right default with idempotent consumers), ordering guarantees (Kafka partitioning gives ordering within a partition — I design partition keys to guarantee ordering where it matters, e.g., all events for a given account on the same partition), and schema evolution (I use Avro or Protobuf with a schema registry to enforce backward-compatible schema evolution).

For webhooks specifically, I design for consumer unreliability — the receiver will be unavailable sometimes. I implement exponential backoff retry with a dead-letter queue for events that exhaust retries, and I expose a replay API so consumers can recover missed events without requiring the producer to re-emit them.

The trade-off I'm honest about with product stakeholders: async systems are harder to debug and harder to reason about end-to-end. I always pair an async architecture with a strong observability investment — correlated trace IDs in event payloads, end-to-end latency metrics that span both producer and consumer, and dead-letter queue monitoring.

Q 07 How do you handle schema evolution in a Kafka-based event-driven platform at scale? ▼

Schema evolution is one of the most operationally dangerous problems in event-driven systems, because a breaking schema change can silently corrupt consumers at runtime — sometimes hours or days after the producer deployed.

My non-negotiable: every Kafka topic has a registered schema in a schema registry (Confluent Schema Registry is the standard). Producers validate messages against the registered schema at publish time. Consumers validate on consumption. This gives you a hard enforcement gate on both sides.

For evolution rules, I enforce backward and forward compatibility as the standard mode: new fields must have defaults, fields can't be removed without a deprecation cycle, and types can't change. That means any existing consumer binary can read new messages, and new consumer binaries can read old messages — you can deploy producers and consumers independently without coordination windows.

For truly breaking changes I use a dual-write migration: the producer writes to both the old and new schema topics in parallel during a migration window, consumers migrate to the new topic, and the old topic is retired once all consumers are confirmed migrated.

I also enforce schema ownership in the CI pipeline: schema changes require a schema registry compatibility check as a mandatory CI step. A PR that introduces an incompatible schema change fails the build before it can be merged, let alone deployed.

Q 08 How do you design PostgreSQL schemas and query patterns for high-throughput, mission-critical financial platforms? ▼

Write path optimization — financial platforms are write-heavy. I design schemas with insert patterns in mind: append-only event tables where possible, UUIDs as primary keys generated client-side (avoiding sequence contention under high concurrency), and partial indexes on high-selectivity filter columns rather than broad composite indexes that bloat write overhead.

Read/write separation — read replicas for reporting and non-transactional queries, with explicit connection routing in the application layer. I never let ad-hoc analytical queries compete with transactional workloads on the primary.

Transaction scope discipline — I keep transactions as short as possible. Long-running transactions hold row locks and bloat the WAL, which kills throughput at scale. In Spring WebFlux with R2DBC, this means explicit transaction boundaries scoped tightly around the critical mutation, not the entire service method.

Partitioning strategy — for high-volume event or transaction tables, range partitioning on timestamp is my default. It keeps hot data in recently active partitions, makes archival clean (drop old partitions instead of bulk deletes), and keeps index sizes manageable.

Connection pool sizing — PostgreSQL is not designed for thousands of direct connections. I use PgBouncer in transaction mode between the application and the database, with pool sizes tuned to the database's max_connections and the application's actual concurrency profile.

Q 09 What's your testing strategy for reactive microservices, and how do you ensure test coverage is meaningful rather than just high? ▼

High coverage percentage is a vanity metric if the tests aren't testing the right things. My testing philosophy for reactive services has three layers.

Unit tests cover pure logic — transformations, business rules, validation. I use StepVerifier from Project Reactor for reactive unit tests — it lets you assert the exact sequence of emissions, errors, and completions on a Flux or Mono without needing a running application context. These run fast and I expect high coverage here.

Integration tests cover the contract between the service and its dependencies: database interactions, external API calls, Kafka produce/consume behavior. I use Testcontainers to spin up real PostgreSQL and Kafka instances in CI — not mocks. Mocking a database in an integration test gives you confidence in the mock, not in your actual query behavior.

Contract tests — using consumer-driven contracts with Pact or Spring Cloud Contract — are the layer most teams skip and most regret skipping. In a microservices platform, an API contract test verifies that a producer's response structure actually matches what the consumer expects. Without it, a producer can ship a breaking change that passes all its own tests and silently breaks a consumer in production.

The "meaningful coverage" standard I apply: can this test catch a regression in a realistic failure mode? If the only way a test fails is if someone deletes the entire method, it's not useful coverage.

Q 10 How do you balance your role as a hands-on technical contributor with the leadership responsibilities of mentoring and driving architecture? ▼

The tension is real and I've had to be deliberate about it. My default is to stay technically engaged enough to have credibility and context — I participate in design reviews, I write code on complex components where I can model the standards I expect, and I do meaningful code reviews rather than rubber-stamp approvals.

But I've learned the hard way that if I'm the one writing critical path code, I've created a bottleneck and I'm not developing my team. So I apply a rule: I design and review, but I don't own delivery on components where a senior engineer can do it. My job is to make them capable of doing it well, not to do it for them.

For mentoring specifically, I use two mechanisms. First, design-level pairing — I involve senior engineers in architecture decisions early, ask them to draft the design doc, and review it with them rather than producing the design myself. Second, structured code review — I use reviews as teaching moments, not just quality gates. A comment that explains why a pattern is preferred is worth ten times a comment that just says "change this."

The metric I use to evaluate myself: is the team making better architectural decisions without me in the room over time? If yes, the leadership approach is working. If they're always waiting for my input before they move, I'm a bottleneck, not a leader.

Q 11 How do you collaborate with product owners to ensure work coming into sprints is well-refined and technically sound? ▼

The failure mode I've seen most often is engineers treating refinement as a passive activity — showing up to backlog grooming, listening to requirements, and nodding along. By the time a story hits the sprint, there are unresolved technical assumptions baked in that surface mid-sprint as blockers.

My approach is to make engineering a first-class participant in the refinement process upstream of grooming. I assign a senior engineer to each in-progress epic as a technical liaison — their job is to be in the product conversations early, raise technical constraints and edge cases before they become story-level surprises, and own the technical acceptance criteria in the story.

In grooming sessions specifically, I use a readiness checklist: is the API contract defined? Are edge cases and error paths documented? Is the data model impact understood? Are external dependencies identified and confirmed available? A story doesn't get a sprint commitment until those are answered.

I also invest in building product owners' technical intuition over time — not to make them engineers, but so they understand why certain requests have architectural implications that need lead time. That relationship investment makes refinement conversations much more productive because we're speaking a common language about trade-offs.
