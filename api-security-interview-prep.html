🔐 API Security Quiz

20 Questions & Answers

1 What's the difference between authentication and authorization?

Authentication verifies who you are - confirming identity (like showing ID at airport security).

Authorization determines what you're allowed to do - checking permissions after identity is confirmed (like your boarding pass determining gate access).

Why you need both: Authentication identifies the user, but doesn't specify permissions. Someone authenticated shouldn't necessarily access all endpoints or data. Together they create secure systems.

2 What is an API rate limit and why implement one?

An API rate limit restricts how many requests a client can make within a time window (e.g., 100 requests/minute).

Two key reasons:

  1. Prevent abuse and DoS attacks - Protects from malicious actors or buggy clients overwhelming the service
  2. Resource management and cost control - Ensures fair usage and prevents single users from consuming disproportionate resources
3 What vulnerability exists in SQL query string concatenation?

Vulnerability: SQL Injection

Vulnerable code: 
const query = `SELECT * FROM users WHERE email = '${req.body.email}'`;

An attacker can inject SQL commands like: admin@example.com' OR '1'='1

Fix: Use parameterized queries:

const query = 'SELECT * FROM users WHERE email = ?';
db.query(query, [req.body.email]);
4 What is CORS and why might it cause errors even with valid API keys?

CORS (Cross-Origin Resource Sharing) is a browser security mechanism controlling whether web pages from one domain can request APIs on different domains.

Why CORS errors occur with valid keys:

CORS is a browser-level check that happens before authentication. If the API doesn't include proper CORS headers (Access-Control-Allow-Origin), the browser blocks the request before your API key is even checked.

Important: CORS errors only happen in browsers, not server-to-server calls or tools like Postman.
5 What are the differences between API keys, OAuth tokens, and JWTs?

API Keys:

  • Simple string identifiers for applications
  • Long-lived, typically don't expire
  • Use: Machine-to-machine, server-to-server (e.g., Google Maps API)

OAuth Tokens:

  • Obtained through OAuth protocol
  • Grant delegated access with specific scopes
  • Short-lived with refresh tokens
  • Use: Accessing user data from third parties (e.g., "Sign in with Google")

JWTs (JSON Web Tokens):

  • Self-contained, digitally signed tokens
  • Stateless - contains user info and permissions
  • Use: Modern authentication in your own APIs, microservices, SSO
6 What is the principle of least privilege in API security?

Granting the minimum level of access necessary to perform a specific function.

Applications in APIs:

  • Endpoint access: Regular users shouldn't access admin endpoints
  • Data scope: Users only see their own data
  • API key permissions: Each key has only needed permissions
  • Token scopes: OAuth/JWT tokens include specific scopes
  • Service accounts: Backend services get minimal permissions

Why it matters: Limits damage if credentials are compromised.

7 What is the OWASP API Security Top 10?

A list by OWASP identifying the most critical security risks for APIs.

Three critical vulnerabilities:

  1. Broken Object Level Authorization (BOLA/IDOR): API doesn't verify users have permission to access specific objects (e.g., changing user ID in URL to access others' data)
  2. Broken Authentication: Weak authentication mechanisms, no rate limiting, exposed session tokens, improperly signed JWTs
  3. Excessive Data Exposure: APIs return more data than necessary, relying on client filtering (e.g., returning password hashes in user objects)
8 Where should JWTs be stored in browsers and what are the tradeoffs?

1. localStorage/sessionStorage

  • ✅ Easy to implement, persists across refreshes
  • ❌ Vulnerable to XSS attacks

2. Cookies (HttpOnly, Secure, SameSite)

  • ✅ Protected from XSS when HttpOnly is set
  • ❌ Vulnerable to CSRF if not properly configured
  • Best practice when properly configured

3. Memory (JavaScript variable)

  • ✅ Most secure against XSS
  • ❌ Poor UX - token lost on refresh
Recommended approach: Store refresh tokens in HttpOnly cookies, keep short-lived access tokens in memory.
9 What is API versioning and why is it important for security?

API versioning maintains multiple API versions simultaneously (e.g., /api/v1/users vs /api/v2/users).

Security importance:

  • Deprecating insecure endpoints: Fix vulnerabilities in v2 while giving clients time to migrate from v1
  • Enforcing stronger security: Require stronger auth in newer versions
  • Removing dangerous features: Eliminate security risks in new versions
  • Compliance: Meet new regulations in v2 while v1 clients transition
  • Controlled rollout: Test security improvements before forcing upgrades
Important: Old versions need deprecation strategies - they can't live forever as permanent attack vectors.
10 What's the difference between encryption in transit and at rest? What does HTTPS provide?

Encryption in transit: Protects data while moving between systems (traveling over networks).

Encryption at rest: Protects data while stored on disk, databases, or backups.

HTTPS provides encryption in transit ONLY.

What HTTPS protects against:

  • Man-in-the-middle attacks
  • Network sniffing
  • ISPs seeing request/response content

What HTTPS does NOT protect:

  • Data stored in databases
  • Data in server logs
  • Data in backups
  • Data accessible with direct server access

Why both are needed: Complete security requires protecting data both during transmission and storage.

11 What is a replay attack and how can you prevent it?

A replay attack occurs when an attacker intercepts a valid API request and re-sends it later to perform unauthorized actions.

Two prevention techniques:

1. Nonces (Number Used Once)

  • Include unique, one-time-use token with each request
  • Server tracks used nonces and rejects duplicates
  • Nonces expire after short time window

2. Timestamps with short expiration

  • Include timestamp in each request
  • Server rejects requests outside acceptable window (e.g., 60 seconds)
  • Often part of JWT or request signature

Bonus: Request signing with timestamps combines both approaches.

12 What's the difference between symmetric and asymmetric encryption for JWTs?

Symmetric encryption:

  • Same key for encryption and decryption
  • Faster and more efficient
  • Examples: AES, DES

Asymmetric encryption:

  • Key pair: public key and private key
  • Slower, more computationally expensive
  • Examples: RSA, ECDSA

For signing JWTs:

Symmetric (HMAC - HS256):

  • Shared secret signs and verifies
  • Use when: Your servers both create and verify tokens

Asymmetric (RS256, ES256):

  • Private key signs, public key verifies
  • Use when: Multiple services verify tokens or third parties need verification
Best practice: Asymmetric is preferred for production, especially in microservices.
13 Why validate input even when using parameterized queries?

Parameterized queries prevent SQL injection but don't protect against:

1. Business logic vulnerabilities

  • Negative quantities in orders
  • Invalid ages or future birthdates

2. Other injection attacks

  • NoSQL injection (MongoDB)
  • Command injection
  • XSS when data is displayed
  • LDAP, XML injection

3. Application crashes

  • Type mismatches causing errors
  • Extremely long strings causing DoS

4. Data integrity issues

  • Garbage data in database
  • Invalid formats breaking functionality
Defense in depth: Input validation and parameterized queries work together as complementary layers.
14 What's the difference between whitelist and blacklist validation?

Whitelist (Allow-list):

  • Define what IS allowed, reject everything else
  • Default: REJECT
  • Example: "Username must be alphanumeric, 3-20 chars"

Blacklist (Deny-list):

  • Define what is NOT allowed, accept everything else
  • Default: ACCEPT
  • Example: "Reject if contains <script>"
Whitelist is MUCH more secure

Why whitelisting is better:

  1. Attackers are creative - Can't anticipate every attack
  2. Bypass techniques - Encoding, obfuscation, variations
  3. Incomplete coverage - Impossible to list all bad inputs
  4. Maintenance burden - Requires constant updates
Example: 
// WEAK - Blacklist
if (username.includes('<') || username.includes('script')) reject();

// STRONG - Whitelist  
if (!/^[a-zA-Z0-9_]{3,20}$/.test(username)) reject();
15 How does "never trust user input" extend beyond the request body?

User input isn't just req.body - attackers can manipulate:

1. URL parameters and query strings

GET /api/users?id=123
GET /api/search?q=<script>alert(1)</script>

2. HTTP headers

  • User-Agent, Referer, X-Forwarded-For can be forged
  • Content-Type manipulation
  • Custom headers like X-API-Key

3. Cookies

  • Can be modified in browser
  • Never trust without validation

4. File uploads

  • File names: ../../../etc/passwd
  • MIME types can be spoofed
  • Malicious file content

5. URL paths

  • Path traversal: /api/users/../../admin/delete

6. Authentication tokens

  • JWTs, OAuth tokens must be validated
Key principle: If it crosses the trust boundary (comes from outside), validate it.
16 What is SSRF and how does it affect APIs accepting URLs?

SSRF (Server-Side Request Forgery) tricks your server into making HTTP requests to unintended locations.

Vulnerable scenarios:

  • Webhook functionality accepting user URLs
  • Image/avatar fetching from URLs
  • PDF generation or screenshot services

What attackers can do:

  1. Access cloud metadata: AWS http://169.254.169.254/latest/meta-data/ to steal credentials
  2. Port scan internal network: http://192.168.1.1:22
  3. Access internal services: http://localhost:6379 (Redis)
  4. Read local files: file:///etc/passwd

Prevention:

  • Whitelist allowed domains/protocols
  • Block private IP ranges and metadata services
  • Disable unnecessary protocols (file://, gopher://)
  • Use separate network segments
  • Validate and sanitize URLs
17 What is API key rotation and why is it important?

API key rotation is periodically replacing API keys with new ones, retiring old keys after a transition period.

Why it's important:

  1. Limits exposure window: Leaked keys from months ago become invalid with rotation
  2. Compartmentalizes breach impact: Know timeframe of potential unauthorized access
  3. Removes forgotten keys: Old integrations and employee keys get cleaned up
  4. Compliance requirements: PCI-DSS, SOC 2, HIPAA require credential rotation
  5. Reduces logging risk: Accidentally logged keys have limited validity

Best practices:

  • Overlapping validity: Generate new key → both valid during transition → revoke old
  • Automated rotation: Use short-lived tokens with auto-rotation
  • Communication: Give consumers advance notice
  • Monitor usage: Track which key is being used
18 What's the difference between horizontal and vertical privilege escalation?

Horizontal Privilege Escalation:

  • Accessing resources of another user at same privilege level
  • Example: User A accesses User B's orders
  • Related to: Broken Object Level Authorization (BOLA/IDOR)
// User 123 changes ID to access User 456's data
GET /api/users/456/orders

Vertical Privilege Escalation:

  • Gaining higher-level permissions than you should have
  • Example: Regular user accesses admin functionality
  • Related to: Broken Function Level Authorization
// Regular user calls admin endpoint
DELETE /api/admin/users/456

Key difference:

  • Horizontal = Same level, wrong user
  • Vertical = Higher level, wrong role

Prevention:

// Prevent Horizontal - check ownership
if (order.userId !== authenticatedUser.id) return 403;

// Prevent Vertical - check role
if (!authenticatedUser.roles.includes('admin')) return 403;
19 What is a timing attack and how is it exploited in authentication?

A timing attack exploits differences in response times to extract sensitive information.

How it works in authentication:

String comparisons often stop at first mismatch, creating timing differences:

  • "aaaaaaaaa" fails immediately → ~1ms
  • "saaaaaaaa" fails on 2nd char → ~2ms
  • "seaaaaaa" fails on 3rd char → ~3ms
  • "secret123key" all match → ~12ms

Attackers measure response times to build the correct key character by character.

Other scenarios:

  • Username enumeration (existing user takes longer)
  • Password reset token validation
  • Account existence checks

Prevention:

  1. Constant-time comparison: 
    const crypto = require('crypto');
crypto.timingSafeEqual(validKey, providedKey);
  2. Artificial delays: Always take minimum time to respond
  3. Consistent processing: Hash password even if username doesn't exist
  4. Rate limiting: Makes collecting timing samples impractical
20 What's the difference between identification, authentication, and authorization?

1. Identification - Who are you claiming to be?

  • User asserts their identity (username, email, user ID)
  • No proof yet - just a claim

2. Authentication - Can you prove it?

  • Verifying the identity claim is legitimate
  • Provides credentials: password, API key, JWT

3. Authorization - What are you allowed to do?

  • Determining permissions/access rights
  • Happens AFTER authentication
  • Checks roles, permissions, resource ownership
Typical flow: 
GET /api/orders/789
Header: Authorization: Bearer eyJhbGc...

1. IDENTIFICATION: Token claims user_id: 123
2. AUTHENTICATION: Validate token signature & expiration  
3. AUTHORIZATION: Does user 123 own order 789?
   → Order belongs to user 456
   → Return 403 Forbidden

Always in this order: Identification → Authentication → Authorization

Common confusion:
  • 401 Unauthorized = authentication failed
  • 403 Forbidden = authorization failed
